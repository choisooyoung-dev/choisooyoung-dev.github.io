MySQL ACID

게시 2026/08/25
By Sooyoung Choi
읽는 시간 8분

트랜잭션이 지켜야 하는 4가지 특성, ACID를 정리해본다.

A - Atomicity (원자성)

트랜잭션 안의 작업들은 전부 성공하거나 전부 실패해야 한다. 중간에 하나라도 실패하면 그 전에 처리된 작업까지 전부 롤백한다.

EX) 재고 차감 + 주문 생성이 하나의 트랜잭션 → 재고 차감은 성공했는데 주문 생성이 실패하면, 재고 차감도 같이 롤백된다.

START TRANSACTION;
UPDATE stock SET quantity = quantity - 1 WHERE product_id = 1;
INSERT INTO orders (product_id, user_id) VALUES (1, 100);

넷 다 성공해야 COMMIT, 하나라도 실패하면 ROLLBACK

C - Consistency (일관성)

트랜잭션 전, 후로 DB가 정해진 규칙(제약조건, FK, 유니크 제약 등)을 항상 만족해야 한다.

EX) 재고 차감 + 로그 기록이 한 세트인데, 재고만 차감되고 로그가 안 남으면 → “재고 변동은 반드시 로그가 남아야 한다”는 업무 규칙이 깨진 것 → 일관성 위반

원자성이 지켜지면 자연스럽게 일관성도 지켜지는 경우가 많지만, 일관성은 DB 제약조건 레벨(FK, CHECK, UNIQUE 등)에서도 별도로 보장된다.

I - Isolation (격리성)

동시에 여러 트랜잭션이 실행돼도 서로 간섭받지 않고, 마치 순차적으로 실행된 것처럼 보여야 한다.

EX) 선착순 100개 쿠폰 이벤트 → “재고 확인” + “재고 차감”을 하나로 묶지 않으면, 두 사람이 동시에 요청했을 때 둘 다 “재고 있음”으로 확인하고 둘 다 차감해버려서 재고가 마이너스가 될 수 있다.

격리성이 보장되면, 한 트랜잭션이 실행되는 동안 다른 트랜잭션이 끼어들지 못하고 기다리게(혹은 각자 다른 스냅샷을 보게) 만들어서 이런 문제를 막는다.

격리 수준(Isolation Level)에 따라 얼마나 엄격하게 격리할지가 달라진다 (READ UNCOMMITTED < READ COMMITTED < REPEATABLE READ < SERIALIZABLE). MySQL(InnoDB)의 기본값은 REPEATABLE READ다.

D - Durability (지속성)

커밋된 트랜잭션의 결과는 서버가 죽어도 사라지면 안 된다. 커밋 시점에 디스크에 기록이 남아있어야 한다.

EX) 주문 완료 후 커밋 → 그 직후 서버가 다운돼도 → 재시작했을 때 그 주문 데이터는 그대로 남아있어야 한다.

InnoDB는 이를 위해 redo log를 사용한다. 커밋 시 실제 데이터 파일에 반영되기 전에도 redo log에 변경 내용을 먼저 기록해두고, 서버가 비정상 종료돼도 재시작 시 redo log를 replay해서 커밋된 데이터를 복구한다.

MySQL(InnoDB)이 ACID를 지키는 방법 (요약)

특성 InnoDB의 구현
Atomicity undo log (실패 시 롤백에 사용)
Consistency 제약조건(FK, UNIQUE, CHECK) + A/I가 지켜지면 자연스럽게 따라옴
Isolation MVCC(다중 버전 동시성 제어) + 잠금(Lock)
Durability redo log (커밋 시 디스크에 기록, 장애 복구에 사용)

트랜잭션 격리 수준 (Isolation Level)

격리성을 완벽하게(간섭 0으로) 만들면 안전하지만 그만큼 성능이 떨어진다. 그래서 MySQL은 “얼마나 엄격하게 격리할지”를 4단계로 선택할 수 있게 해준다. 엄격할수록 안전하지만 느려지는 trade-off 관계다.

단계 설명 발생 가능한 문제
READ UNCOMMITTED 다른 트랜잭션이 아직 커밋하지 않은(진행 중인) 데이터도 그냥 읽어버림 Dirty Read — 실무에서 거의 사용하지 않음
READ COMMITTED 커밋된 데이터만 읽음. PostgreSQL, Oracle의 기본값 Non-repeatable Read — 같은 트랜잭션 안에서 같은 쿼리를 두 번 실행했는데, 그 사이에 다른 트랜잭션이 커밋한 값이 반영돼서 결과가 달라질 수 있음
REPEATABLE READ 트랜잭션 시작 시점의 스냅샷을 기준으로 계속 같은 값을 읽음 (트랜잭션이 끝날 때까지 일관됨). MySQL, MariaDB의 기본값 Non-repeatable Read는 해결되지만, 특정 조건에서 Phantom Read 가능성은 남음
SERIALIZABLE 모든 트랜잭션을 거의 순서대로(직렬로) 처리 문제는 제일 적지만, 동시 처리 성능이 크게 떨어져서 실무에서 거의 안 씀

격리 수준만으로 선착순 쿠폰이 지켜질까?

EX) 선착순 쿠폰 100개, 두 사람이 동시에 요청한다면? REPEATABLE READ만으로 정확히 100개만 발급되는 게 보장될까?

아니다. REPEATABLE READ가 보장하는 건 “읽기”의 일관성이지, “쓰기”의 순서가 아니다.

  • 두 트랜잭션이 동시에 같은 행(row)을 수정하려 할 때, 격리 수준 자체는 “누가 먼저 쓸지” 순서를 정해주는 장치가 아니다.
  • 실제로 순서를 강제하려면 명시적 락(LOCK)이 별도로 필요하다. 해당 row에 락을 걸어서, 다 쓸 때까지 다른 트랜잭션은 기다리게 강제해야 한다.

즉 격리 수준(읽기 일관성)과 락(쓰기 순서 보장)은 서로 다른 역할이며, 동시성이 중요한 로직(재고 차감, 선착순 이벤트 등)에는 격리 수준만 믿지 말고 락을 함께 고려해야 한다.

정리

ACID는 각각 독립된 개념이라기보다, 트랜잭션이 안전하게 동작하기 위해 서로 맞물려 있는 4가지 측면이다. 원자성과 일관성이 “정확성”을 보장한다면, 격리성은 “동시성 상황에서의 정확성”, 지속성은 “장애 상황에서의 정확성”을 보장하는 셈이다.
