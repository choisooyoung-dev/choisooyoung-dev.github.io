MySQL 문자셋(Character Set)과 Collation

문자셋(Character Set)과 Collation의 차이, utf8mb4를 써야 하는 이유, 대소문자 구분 collation까지 정리한다.

게시 2026/08/31
By Sooyoung Choi
읽는 시간 6분

문자셋(Character Set)

문자를 저장할 때 어떤 바이트로 인코딩할지 정하는 것. 같은 문자라도 문자셋에 따라 몇 바이트로, 어떤 값으로 저장되는지가 달라진다.

Collation

문자열을 비교하고 정렬할 때 어떤 규칙을 쓸지 정하는 것. 같은 문자셋이어도 collation에 따라 a와 A를 같은 걸로 볼지, 가와 나 중 뭐가 먼저인지가 달라진다.

즉 문자셋 = 저장 방식, collation = 비교/정렬 규칙으로 역할이 나뉜다. 하나의 문자셋에는 보통 여러 개의 collation이 딸려 있고, 그중 하나를 골라서 쓰는 구조다.

1

SHOW COLLATION WHERE Charset = 'utf8mb4';

MySQL에서 꼭 알아야 하는 함정: utf8 vs utf8mb4

MySQL의 utf8은 사실 진짜 UTF-8이 아니다. 문자 1개당 최대 3바이트까지만 지원한다. 그런데 이모지(😀)나 일부 한자는 4바이트가 필요하다 — 즉 utf8로 설정된 컬럼에 이모지를 저장하려고 하면 에러가 나거나 깨진다.

  • utf8: 최대 3바이트. 이모지 저장 불가.
  • utf8mb4: 최대 4바이트. 진짜 완전한 UTF-8. 이모지, 일부 한자 다 지원.

이름 때문에 자주 헷갈리는데, utf8mb4가 진짜 표준 UTF-8이고 utf8은 MySQL 초기에 만들어진 반쪽짜리 구현이 그대로 이름으로 굳어진 것이다. 지금 새로 테이블/DB를 만든다면 무조건 utf8mb4를 써야 한다.

1
2
3
4

CREATE TABLE posts (
  id BIGINT PRIMARY KEY,
  title VARCHAR(255)
) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

Collation 이름 읽는 법

utf8mb4_0900_ai_ci 같은 이름은 규칙이 있다.

1
2

utf8mb4  _  0900   _  ai        _  ci
문자셋      버전(대략)   억양 구분     대소문자 구분
  • ai (accent-insensitive): 억양 부호(é, e처럼) 구분 안 함. as면 구분함.
  • ci (case-insensitive): 대소문자 구분 안 함 (a = A로 취급)
  • cs (case-sensitive): 대소문자 구분함 (a ≠ A)
  • bin: 문자를 그대로 바이너리(바이트값)로 비교. 가장 엄격함, 대소문자/억양 다 구분.
Collation WHERE name = 'abc'로 ABC 검색 시
utf8mb4_general_ci / utf8mb4_0900_ai_ci 매칭됨 (대소문자 구분 안 함)
utf8mb4_0900_as_cs 매칭 안 됨 (대소문자 + 억양 구분)
utf8mb4_bin 매칭 안 됨 (바이트 그대로 비교)

로그인 아이디, 이메일처럼 대소문자를 구분해야 하는 컬럼이라면 _ci 계열이 아니라 _bin이나 _cs 계열을 써야 의도한 대로 동작한다. 반대로 일반적인 검색/정렬용 텍스트는 보통 _ci가 사용자 입장에서 자연스럽다 (검색할 때 대소문자 안 가리고 찾아지는 게 편하니까).

실무에서 문제가 되는 경우

1. 컬럼마다 charset/collation이 다를 때 JOIN 에러

1
2

Illegal mix of collations (utf8mb4_general_ci,IMPLICIT) and
(utf8mb4_0900_ai_ci,IMPLICIT) for operation '='

서로 다른 collation을 가진 컬럼끼리 비교/조인하면 이런 에러가 난다. DB/테이블/컬럼을 만들 때 문자셋과 collation을 일관되게 맞춰두는 게 중요한 이유다.

2. 이미 운영 중인 테이블이 utf8(3바이트)로 되어 있을 때

이모지가 포함된 데이터를 저장하려다 에러가 나거나, 이모지만 잘려서 저장된다. 이 경우 utf8mb4로 변환해줘야 한다.

1
2

ALTER TABLE posts
  CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

데이터가 많은 테이블에서 이 작업은 테이블 전체를 다시 쓰는 무거운 작업이라, 운영 중인 서비스라면 트래픽이 적은 시간대에 진행하거나 온라인 스키마 변경 도구(gh-ost, pt-online-schema-change 등)를 고려해야 한다.

-- 특정 테이블의 컬럼별 문자셋/collation
SELECT COLUMN_NAME, CHARACTER_SET_NAME, COLLATION_NAME
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = 'my_db' AND TABLE_NAME = 'posts';

정리

  • 문자셋은 “어떻게 저장할지”(바이트 인코딩), collation은 “어떻게 비교/정렬할지”를 정한다.
  • MySQL의 utf8은 최대 3바이트라 이모지를 못 담는다 — 항상 utf8mb4를 써야 한다.
  • Collation 이름의 _ci/_cs/_bin으로 대소문자 구분 여부가 정해진다. 로그인 ID처럼 구분이 필요한 곳엔 _ci를 쓰면 안 된다.
  • DB/테이블/컬럼마다 charset·collation이 다르면 JOIN/비교에서 에러가 날 수 있으므로, 프로젝트 전체에서 일관되게 맞춰두는 게 좋다.
