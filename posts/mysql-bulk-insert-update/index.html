벌크 INSERT/UPDATE 최적화

여러 건을 한 건씩 INSERT/UPDATE할 때 느려지는 이유와, 멀티 밸류 INSERT·배치 처리·INSERT ... ON DUPLICATE KEY UPDATE로 최적화하는 방법을 정리한다.

게시 2026/09/03
By Sooyoung Choi
읽는 시간 5분

수천~수만 건을 저장해야 할 때 for문 안에서 INSERT 한 번씩 날리면 눈에 띄게 느리다. 왜 느린지, 어떻게 줄이는지 정리한다.

한 건씩 처리하면 왜 느린가

1
2
3
4

INSERT INTO log (user_id, message) VALUES (1, 'a');
INSERT INTO log (user_id, message) VALUES (2, 'b');
INSERT INTO log (user_id, message) VALUES (3, 'c');
-- 1만 번 반복
  • 쿼리 한 번마다 네트워크 왕복(round trip) 이 발생한다. 애플리케이션 ↔ DB 간 지연시간이 쿼리 실행 시간보다 더 큰 비중을 차지하게 된다.
  • 각 INSERT가 개별 트랜잭션으로 커밋되면(autocommit 상태), 매번 디스크에 로그를 플러시하는 비용도 같이 든다.
  • 인덱스가 있다면 매 삽입마다 인덱스 갱신 비용도 1만 번 반복된다.

멀티 밸류 INSERT

1
2
3
4

INSERT INTO log (user_id, message) VALUES
  (1, 'a'),
  (2, 'b'),
  (3, 'c');
  • 한 번의 쿼리, 한 번의 네트워크 왕복으로 여러 row를 넣는다. 왕복 횟수가 N번 → 1번으로 줄어드는 게 핵심 이득이다.
  • 다만 한 쿼리에 너무 많은 row를 몰아넣으면 max_allowed_packet 제한에 걸리거나, 실패했을 때 전체가 롤백되어 원인 파악이 어려워진다. 보통 500~1000건 단위로 잘라서 배치 처리한다.
1

-- 1만 건을 1000건씩 10번의 쿼리로 나눠 실행

트랜잭션으로 묶기

멀티 밸류가 어려운 상황(ex. 각 row마다 다른 로직이 필요)이라면, 최소한 여러 개의 단건 쿼리를 하나의 트랜잭션으로 묶는다.

1
2
3
4
5

BEGIN;
INSERT INTO log (user_id, message) VALUES (1, 'a');
INSERT INTO log (user_id, message) VALUES (2, 'b');
-- ...
COMMIT; -- 여기서 한 번만 디스크 플러시
  • autocommit 상태에서 쿼리마다 커밋하는 것보다, 묶어서 한 번에 커밋하면 디스크 flush 횟수가 줄어 훨씬 빠르다.
  • 대신 트랜잭션이 길어지면 락을 오래 잡게 되므로 다른 트랜잭션과의 경합이 늘어날 수 있다 — 배치 크기를 적당히 쪼개야 하는 이유가 여기에도 있다.

UPDATE는 어떻게

UPDATE는 INSERT처럼 한 문장에 여러 row를 값별로 다르게 넣는 표준 문법이 없다. 대신 자주 쓰는 두 가지 방법이 있다.

1. CASE WHEN으로 한 문장에 묶기

1
2
3
4
5
6
7

UPDATE product
SET price = CASE id
  WHEN 1 THEN 1000
  WHEN 2 THEN 2000
  WHEN 3 THEN 3000
END
WHERE id IN (1, 2, 3);
  • 한 번의 쿼리로 여러 row를 서로 다른 값으로 갱신한다.
  • id 개수가 너무 많아지면 쿼리 자체가 비대해지므로, 이것도 배치 단위로 잘라 쓰는 게 좋다.

2. INSERT ... ON DUPLICATE KEY UPDATE (upsert)

1
2
3
4
5
6

INSERT INTO product (id, price) VALUES
  (1, 1000),
  (2, 2000),
  (3, 3000)
AS new
ON DUPLICATE KEY UPDATE price = new.price;
  • id가 이미 있으면 UPDATE, 없으면 INSERT — 삽입과 갱신을 한 번에 처리할 때 유용하다.
  • 멀티 밸류 INSERT와 동일하게 한 번의 왕복으로 여러 row를 처리하므로 벌크 upsert에 자주 쓰인다.

정리

  • 반복문으로 단건 쿼리를 날리면 네트워크 왕복 + 커밋(flush) 비용이 row 수만큼 누적돼서 느리다.
  • INSERT는 멀티 밸류 문법으로, 적당한 배치 크기(수백~1000건)로 잘라서 묶어 보낸다.
  • 단건 쿼리를 묶어야 한다면 최소한 트랜잭션으로 감싸서 커밋 횟수를 줄인다.
  • UPDATE는 CASE WHEN 또는 INSERT ... ON DUPLICATE KEY UPDATE 로 여러 row를 한 번에 처리한다.
  • 배치가 너무 크면 트랜잭션이 길어져 락 경합이 커지고, max_allowed_packet 제한에도 걸릴 수 있으므로 적당한 크기로 쪼개는 균형이 필요하다.
