MySQL 파티셔닝(Partitioning) - 한 서버에서 테이블 쪼개기

MySQL 파티셔닝의 개념과 파티션 프루닝, DELETE/DROP PARTITION 예시, 주의사항을 정리한다.

게시 2026/08/31
By Sooyoung Choi
읽는 시간 10분

복제(Replication)가 여러 서버로 데이터를 나누는 방법이었다면, 파티셔닝은 한 서버 안에서 테이블을 쪼개는 방법이다.

파티셔닝이란

논리적으로는 하나의 테이블이지만, 물리적으로는 내부에서 여러 조각(파티션)으로 나누어 저장하는 기능. 애플리케이션 입장에서는 그냥 orders 테이블 하나에 쿼리를 날리는 것처럼 보이지만, MySQL 내부적으로는 조건에 맞는 파티션만 골라서 처리한다.

CREATE TABLE orders (
  id INT NOT NULL,
  created_at DATE NOT NULL,
  amount INT,
  PRIMARY KEY (id, created_at)
)
PARTITION BY RANGE (YEAR(created_at) * 100 + MONTH(created_at)) (
  PARTITION p202501 VALUES LESS THAN (202502),
  PARTITION p202502 VALUES LESS THAN (202503),
  PARTITION p202503 VALUES LESS THAN (202504),
  PARTITION p_future VALUES LESS THAN MAXVALUE
);

이렇게 만들면 orders라는 테이블 하나 안에, p202501, p202502, p202503, p_future라는 물리적으로 분리된 저장공간이 생긴다. created_at이 2025년 1월인 행은 p202501에, 2월인 행은 p202502에 저장되는 식이다.

장점: 파티션 프루닝 (Partition Pruning)

프루닝이 뭔데?

프루닝(pruning)은 “가지치기”라는 뜻이다. 나무에서 필요 없는 가지를 잘라내듯, 쿼리를 실행하기도 전에 “이 파티션은 볼 필요가 없다”고 미리 걸러내는 것을 파티션 프루닝이라고 부른다.

파티셔닝을 안 한 일반 테이블은, 인덱스가 있어도 결국 하나의 큰 저장공간 안에서 검색한다. 하지만 테이블이 여러 파티션(= 물리적으로 나뉜 여러 개의 작은 테이블)으로 쪼개져 있으면, MySQL 옵티마이저는 쿼리를 실행하기 전에 “WHERE 조건을 만족하는 행이 있을 수 있는 파티션이 어디어디인지”부터 계산한다. 그리고 그 계산 결과, 조건과 전혀 무관한 게 확실한 파티션은 아예 열어보지도 않고 건너뛴다. 이 “미리 걸러내서 건너뛰는” 과정 자체가 프루닝이다.

1
2
3

SELECT * FROM orders
WHERE created_at BETWEEN '2025-02-01' AND '2025-02-28';
-- p202502 파티션만 조회. 다른 파티션(1월, 3월, ...)은 아예 스캔하지 않는다.

이 쿼리를 보면 MySQL은 파티션을 나눈 기준(created_at의 연/월)을 보고 “2025년 2월 데이터는 p202502에만 있을 수 있다”는 걸 알고 있으므로, p202501이나 p202503 같은 다른 파티션은 그 안에 조건에 맞는 데이터가 있을 리가 없다는 걸 이미 알기 때문에 아예 뒤져보지 않는다.

전체 데이터가 몇 건이든, 해당 파티션 안에서만 찾으면 되므로 속도가 크게 빨라진다. 마치 문서를 연도별 서랍에 나눠 보관해두면, “2025년 2월 문서”를 찾을 때 다른 서랍은 아예 열어보지도 않고 그 서랍 하나만 뒤지면 되는 것과 같다.

실제로 프루닝됐는지 확인하기

EXPLAIN에 partitions 컬럼을 같이 보면(EXPLAIN PARTITIONS 또는 그냥 EXPLAIN에도 최신 버전은 partitions 컬럼이 포함됨), 실제로 어떤 파티션만 조회 대상이 됐는지 확인할 수 있다.

1
2

EXPLAIN SELECT * FROM orders
WHERE created_at BETWEEN '2025-02-01' AND '2025-02-28';

결과의 partitions 컬럼에 p202502처럼 딱 필요한 파티션 이름만 나오면 프루닝이 제대로 동작하고 있는 것이다. 만약 p202501,p202502,p202503,p_future처럼 전체 파티션이 다 나온다면, 프루닝이 안 먹히고 있다는(= 조건이 파티션 키를 제대로 못 쓰고 있다는) 신호다.

DELETE에도 똑같이 적용된다

1
2
3

DELETE FROM orders
WHERE created_at BETWEEN '2025-02-01' AND '2025-02-28';
-- p202502 파티션만 훑어서 지운다. 다른 파티션은 건드리지 않음.

SELECT뿐 아니라 DELETE, UPDATE도 파티션 프루닝의 혜택을 받는다. 조건에 파티션 키가 들어가 있으면, 지워야 할 행을 찾기 위해 전체 테이블을 스캔할 필요가 없다.

로그성 데이터 정리는 DROP PARTITION이 더 낫다

특정 월의 데이터를 통째로 지워야 하는 상황(오래된 로그 정리 등)이라면, DELETE보다 DROP PARTITION이 훨씬 빠르다.

1

ALTER TABLE orders DROP PARTITION p202501;

DELETE는 조건에 맞는 행을 한 줄씩 찾아서 지우고 그 과정이 다 로그(binlog, undo log)에 남는 무거운 작업이지만, DROP PARTITION은 그 파티션이 저장된 파일 자체를 통째로 버리는 작업이라 몇백만 건이 들어있어도 순식간에 끝난다. 그래서 “로그성 데이터를 주기적으로 정리해야 하는 경우”에 파티셔닝이 특히 많이 쓰인다 — 예를 들어 매달 파티션을 하나씩 새로 만들고, N개월이 지난 파티션은 DROP PARTITION으로 정리하는 식이다.

주의할 점

  • 파티션 기준 컬럼이 WHERE에 없으면 프루닝이 안 먹힌다. 이 경우 전체 파티션을 다 훑어야 해서, 파티셔닝을 안 한 것과 성능 차이가 없거나 오히려 관리 부담만 늘어난다.
  • PK/UNIQUE 제약에는 파티션 기준 컬럼이 포함되어야 한다. (위 예제에서 PRIMARY KEY (id, created_at)처럼 파티션 키인 created_at이 PK에 같이 들어간 이유) MySQL은 파티션 간에 유니크 제약을 보장할 수 없어서, 파티션 키 없이는 PK/UNIQUE를 걸 수 없다는 제약이 있다.
  • 작은 테이블에 파티션을 걸면 이득이 없다. 파티션 나누기/관리하는 복잡도만 늘어나고, 어차피 전체 스캔해도 빠른 크기라면 굳이 나눌 이유가 없다.
  • WHERE 절에 파티션 키가 실제로 자주 쓰일 때만 효과가 있다. 조회 패턴이 파티션 키와 무관하게 다양하다면, 파티셔닝의 장점(프루닝)을 거의 못 누리게 된다.

정리

  • 파티셔닝은 하나의 테이블을 내부적으로 여러 물리적 조각으로 나눠 저장하는 기능이다.
  • 파티션 프루닝 덕분에, 조건에 파티션 키가 있으면 관련 파티션만 조회/수정/삭제해서 빨라진다 (SELECT, DELETE, UPDATE 전부 해당).
  • 로그성 데이터를 주기적으로 정리해야 한다면, DELETE보다 DROP PARTITION이 훨씬 효율적이다.
  • 파티션 키가 WHERE에 자주 등장하는 큰 테이블에만 효과가 있고, 작은 테이블이나 파티션 키를 안 쓰는 조회 패턴에는 오히려 복잡도만 늘어난다.
