MySQL 클러스터드 인덱스 · 커버링 인덱스 · 복합 인덱스

클러스터드 인덱스, 커버링 인덱스, 복합 인덱스의 컬럼 순서(카디널리티)까지 EXPLAIN 예제와 함께 정리한다.

게시 2026/08/25
By Sooyoung Choi
읽는 시간 9분

지난 글(MySQL 인덱스 자료구조 - B+Tree)에 이어서, 인덱스의 종류와 복합 인덱스 설계 방법을 정리한다.

클러스터드 인덱스 (Clustered Index) = PK 인덱스

InnoDB는 PK로 만든 인덱스가 있으면, 테이블의 실제 데이터(Row) 자체가 그 B+Tree의 리프 노드에 저장된다. 이걸 클러스터드 인덱스라고 부른다.

  • PK로 조회할 때: B+Tree를 타고 내려가서 리프 노드에 도착하면, 그 자리에 바로 실제 데이터가 있다. 한 번에 끝난다.
  • PK가 아닌 걸로 조회할 때 (유니크 인덱스 등, = 세컨더리 인덱스): 이 인덱스의 B+Tree 리프에는 실제 데이터가 아니라 PK 값만 저장되어 있다.
    1. 세컨더리 인덱스를 타고 내려가 리프에서 PK를 찾는다.
    2. 그 PK로 다시 클러스터드 인덱스(PK 인덱스)를 타고 내려가서 진짜 데이터를 찾는다.
      • 이 2번째 단계를 “back to table lookup” 이라고 부른다. 조회를 두 번 하는 셈이라 PK로 직접 조회하는 것보다 느리다.

커버링 인덱스 (Covering Index)

PK가 아닌 컬럼으로 조회하면 원래는 세컨더리 인덱스 → back to table lookup까지 거쳐야 한다. 그런데 SELECT하는 컬럼이 전부 그 세컨더리 인덱스에 이미 포함된 값이라면?

→ 클러스터드 인덱스까지 갈 필요 없이, 세컨더리 인덱스만 보고 바로 조회가 끝난다. 이런 상태를 “인덱스가 쿼리를 커버한다(covering)“고 하고, 이 인덱스를 커버링 인덱스라고 부른다.

EX) order_num, status 두 컬럼으로 복합 인덱스가 걸려 있다고 하면

1
2
3

SELECT order_num, status
FROM discount_order
WHERE order_num = '20250825-0000213';

SELECT하는 컬럼(order_num, status)이 전부 인덱스에 포함되어 있으므로, back to table lookup 없이 인덱스만으로 끝난다.

EXPLAIN으로 확인하기

1
2
3
4

EXPLAIN
SELECT order_num, status
FROM discount_order
WHERE order_num = '20250825-0000213';
id select_type table type possible_keys key key_len ref rows Extra
1 SIMPLE discount_order ref idx_order_status idx_order_status 42 const 1 Using index

Extra 컬럼에 Using index가 찍히면 커버링 인덱스로 처리됐다는 뜻이다. 만약 SELECT *로 바꾸거나, 인덱스에 없는 컬럼을 하나라도 조회하면 이 값이 사라지고 대신 실제 데이터를 찾으러 가는 과정(back to table lookup)이 추가된다.

참고로 Extra에 Using index condition이 찍히는 경우도 있는데, 이건 커버링과는 다르게 인덱스로 조건은 걸러내지만 최종적으로는 테이블(클러스터드 인덱스)까지 가서 데이터를 가져오는 경우다. 순수하게 인덱스만으로 끝나는 건 Using index뿐이다.

실무에서 SELECT *를 지양하는 이유

  1. 필요 없는 데이터까지 네트워크로 전송하게 된다. (컬럼이 많을수록, 행이 많을수록 낭비가 커짐)
  2. 커버링 인덱스로 최적화될 기회를 날린다. 필요한 컬럼만 명시했다면 인덱스만으로 끝났을 조회가, * 때문에 인덱스에 없는 컬럼까지 필요해져서 back to table lookup이 강제로 발생한다.

복합 인덱스 (Composite Index)

여러 컬럼을 묶어서 만드는 인덱스. INDEX (userId, createdAt)처럼 두 개 이상의 컬럼을 하나의 인덱스로 만든다.

카디널리티 (Cardinality)

한 컬럼에 서로 다른 값이 몇 종류나 있는지를 나타내는 지표.

  • status (예: enum('pending','done','cancelled')) → 값의 종류가 몇 개 안 됨 → 카디널리티 낮음
  • userId → 사용자마다 거의 다 다른 값 → 카디널리티 높음

카디널리티가 높을수록, 그 컬럼으로 조건을 걸었을 때 후보군이 확 줄어든다 (= 검색이 잘 좁혀진다).

복합 인덱스의 컬럼 순서

원칙: 동등 비교(=) 컬럼을 먼저, 범위 비교(>, <, BETWEEN 등) 컬럼을 뒤에. 그리고 그중에서도 카디널리티가 높은(잘 좁혀주는) 컬럼을 앞에 둔다.

EX)

1

WHERE userId = 5 AND createdAt > '2026-09-01';

userId는 =(동등 비교, 카디널리티 높음), createdAt은 >(범위 비교) → 인덱스는 (userId, createdAt) 순서로 만든다.

(userId, createdAt) 순서로 만들면

userId로 먼저 크게 좁힌 다음, 그 안에서만 createdAt이 정렬되어 있다.

                    /         |          \

userId = 5로 검색하면 트리 한 번에 해당 그룹으로 바로 이동하고, 그 안에서 createdAt도 이미 정렬돼 있어서 범위 조건까지 한 번에 빠르게 훑을 수 있다.

반대로 (createdAt, userId) 순서로 만들면?

createdAt(범위 비교 컬럼)이 먼저 오면, userId = 5 조건이 있어도 날짜별로 흩어진 모든 그룹을 다 헤집고 다녀야 userId = 5인 행들을 모을 수 있다.

     |        |       |       |            |
  (그 안에서 userId 값들이 순서 없이 흩어져 있음)
     |
  userId: 3, 7, 8, ...

userId = 5인 행이 여러 날짜에 걸쳐 흩어져 있으므로, 거의 모든 리프를 다 확인해야 한다. → 인덱스를 걸어놨는데도 사실상 전체 스캔에 가깝게 동작한다.

정리

  • 클러스터드 인덱스(PK): 리프에 실제 데이터가 있다. PK 조회가 제일 빠른 이유.
  • 세컨더리 인덱스: 리프에 PK만 있어서, 데이터를 찾으려면 PK로 한 번 더 조회(back to table lookup)해야 한다.
  • 커버링 인덱스: SELECT 컬럼이 전부 인덱스에 있으면 back to table lookup 없이 인덱스만으로 끝난다 (Extra: Using index).
  • SELECT *는 네트워크 낭비 + 커버링 인덱스 기회 상실이라는 두 가지 이유로 지양한다.
  • 복합 인덱스는 (동등 비교 컬럼, 범위 비교 컬럼) 순서로, 그중에서도 카디널리티 높은 컬럼을 앞에 두는 게 원칙이다. 순서가 뒤바뀌면 인덱스가 있어도 사실상 못 쓰는 것과 비슷해질 수 있다.
