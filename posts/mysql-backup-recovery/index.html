MySQL 백업/복구 전략

논리 백업(mysqldump)과 물리 백업(스냅샷)의 차이, 바이너리 로그를 이용한 특정 시점 복구(PITR), 복제와 백업의 역할 차이를 정리한다.

게시 2026/09/03
By Sooyoung Choi
읽는 시간 6분

장애가 났을 때 “복제 서버가 있으니까 괜찮다”고 착각하기 쉽지만, 복제는 백업이 아니다. 실수로 데이터를 지운 DELETE도 그대로 복제되기 때문이다. 백업과 복구 전략을 별도로 정리한다.

논리 백업 vs 물리 백업

논리 백업 (Logical Backup) — mysqldump

1

mysqldump -u root -p --single-transaction --routines --triggers mydb > backup.sql
  • 데이터를 SQL 문(INSERT 등) 으로 덤프한다. 사람이 읽을 수 있고, 다른 MySQL 버전이나 스토리지 엔진으로도 복원 가능.
  • --single-transaction 옵션을 주면 InnoDB 기준으로 트랜잭션 격리를 이용해 덤프 도중에도 서비스를 멈추지 않고 일관된 스냅샷을 뜰 수 있다 (MVCC 덕분에 잠금 없이 가능).
  • 단점: 데이터가 많으면 덤프/복원 모두 느리다. 복원 시 SQL을 처음부터 다시 실행하는 것이므로 대용량 DB에서는 시간이 오래 걸린다.

물리 백업 (Physical Backup) — 파일 스냅샷

1
2

# 예: Percona XtraBackup, 또는 볼륨 스냅샷(EBS snapshot 등)
xtrabackup --backup --target-dir=/backup/
  • InnoDB의 실제 데이터 파일(.ibd)을 그대로 복사한다.
  • 대용량 DB에서 mysqldump보다 백업/복구 속도가 훨씬 빠르다 (파일 복사 수준).
  • 단점: 같은 MySQL 버전·환경에서만 안전하게 복원 가능. 사람이 내용을 읽거나 부분적으로 수정하긴 어렵다.

바이너리 로그와 특정 시점 복구 (PITR)

전체 백업만으로는 백업 시점 이후의 변경사항을 복구할 수 없다. 이를 메꾸는 게 바이너리 로그(Binary Log, binlog) 다.

  • binlog는 데이터를 변경하는 모든 쿼리(INSERT/UPDATE/DELETE/DDL)를 순서대로 기록한다. 복제에서 복제 서버로 변경사항을 전달하는 데도 쓰이는 바로 그 로그다.
  • 복구 절차:
    1. 가장 최근의 전체 백업을 복원한다 (ex. 매일 새벽 3시 백업).
    2. 백업 시점 이후의 binlog를 그 다음부터 순서대로 재생(replay)한다.
    3. 장애 직전(ex. 실수로 DELETE 실행하기 직전) 시점까지만 재생하면, 그 시점 상태로 복구할 수 있다. 이게 PITR(Point-In-Time Recovery) 다.
1
2

# 백업 이후의 binlog를, 실수한 쿼리 직전 시각까지만 재생
mysqlbinlog --stop-datetime="2026-09-03 09:59:00" mysql-bin.000123 | mysql -u root -p mydb

전체 백업만 있고 binlog가 없으면 마지막 백업 시점까지만 되돌릴 수 있다. binlog가 있어야 “장애 직전”까지 복구 범위를 좁힐 수 있다.

복제(Replication)는 백업이 아니다

  • 복제는 가용성을 위한 것이다 — 마스터가 죽었을 때 즉시 대체할 서버를 두는 목적.
  • 복제는 마스터에서 일어난 변경을 그대로 복제 서버에도 반영한다. 실수로 DROP TABLE을 실행하면 그 즉시 복제 서버에서도 테이블이 사라진다.
  • 즉, 복제는 “서버가 죽는” 장애에는 강하지만 “잘못된 쿼리를 실행한” 장애에는 아무 도움이 안 된다. 이건 반드시 별도의 백업(+ binlog)으로만 복구할 수 있다.

실무에서 흔히 쓰는 조합

  • 전체 백업: 매일 1회(새벽) 물리 백업(대용량) 또는 논리 백업(소규모).
  • binlog: 상시 보관(최소 며칠~몇 주 분량) — PITR에 필수.
  • 복제: 장애 시 즉시 전환(failover)용 — 백업과는 목적이 다르므로 같이 운용.
  • 백업 파일은 DB 서버와 물리적으로 분리된 저장소(다른 서버, 클라우드 스토리지)에 보관 — DB 서버 자체가 사라지는 사고에 대비.
  • 백업은 만들어두는 것보다 주기적으로 실제 복원 테스트를 해보는 게 훨씬 중요하다. 복원이 안 되는 백업은 없는 것과 같다.

정리

  • 논리 백업(mysqldump) 은 이식성이 좋고, 물리 백업(파일 스냅샷) 은 대용량에서 빠르다.
  • binlog를 같이 보관해야 전체 백업 시점 이후의 변경분까지 재생해서 특정 시점(PITR) 으로 복구할 수 있다.
  • 복제는 백업이 아니다 — 서버 장애 대비지, 사람의 실수(잘못된 DELETE/DROP)는 복구해주지 못한다.
  • 백업은 “만들어뒀다”가 아니라 “복원해봤다”까지 확인해야 진짜 안전하다.
