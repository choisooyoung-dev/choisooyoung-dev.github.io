페이지네이션 - OFFSET vs Cursor 기반

OFFSET 기반과 Cursor 기반 페이지네이션의 차이, 성능 문제, TypeORM 예시와 복합 정렬 기준 커서 만드는 법까지 정리한다.

게시 2026/08/31
By Sooyoung Choi
읽는 시간 10분

OFFSET 기반 페이지네이션

가장 흔히 쓰는 방식. “몇 번째부터 몇 개를 가져와라”를 지정한다.

1
2

SELECT * FROM posts ORDER BY id DESC LIMIT 10 OFFSET 20;
-- 21번째부터 10개 (3페이지, 페이지당 10개 기준)

TypeORM 예시

1
2
3
4
5

const posts = await postRepository.find({
  order: { id: 'DESC' },
  take: 10,
  skip: (page - 1) * 10, // page=3이면 skip=20
});

문제: 뒤 페이지로 갈수록 느려진다

OFFSET 20이면 DB는 실제로는 앞의 20개를 다 읽고 버린 다음, 그 뒤 10개를 가져온다. OFFSET 100000이면 10만 건을 읽고 다 버린 다음에야 원하는 10개를 주는 것이다.

1
2
3
4
5

-- 1페이지: 거의 즉시
SELECT * FROM posts ORDER BY id DESC LIMIT 10 OFFSET 0;

-- 10000페이지: 앞의 99,990건을 다 읽고 버린 뒤에야 응답
SELECT * FROM posts ORDER BY id DESC LIMIT 10 OFFSET 99990;

OFFSET 값이 커질수록 낭비되는 스캔량이 계속 늘어난다. 인덱스가 있어도 이 문제는 근본적으로 해결이 안 된다 — 인덱스는 “정렬된 순서로 빠르게 읽는 것”은 도와주지만, “앞부분을 건너뛰는 것” 자체는 결국 그만큼 읽어야 하기 때문이다.

Cursor 기반 페이지네이션

“몇 번째부터”가 아니라 “이 값 다음부터”로 가져온다. 보통 정렬 기준 컬럼(예: id)의 마지막 값을 커서로 쓴다.

1
2
3
4
5

-- 1페이지: 최신 10개
SELECT * FROM posts ORDER BY id DESC LIMIT 10;
-- 마지막으로 받은 게 id=91이라면, 다음 페이지는:
SELECT * FROM posts WHERE id < 91 ORDER BY id DESC LIMIT 10;
-- 그다음 페이지는 그때 받은 마지막 id를 또 커서로 사용

id에 인덱스가 있으면, WHERE id < 91은 인덱스를 타고 바로 그 지점부터 읽기 시작한다. 앞부분을 읽고 버리는 낭비가 없어서, 몇 페이지를 가든 속도가 거의 일정하다.

TypeORM 예시

async function getNextPage(cursor?: number) {
  return postRepository.find({
    where: cursor ? { id: LessThan(cursor) } : {},
    order: { id: 'DESC' },
    take: 10,
  });
}

// 사용
const firstPage = await getNextPage(); // cursor 없음 → 첫 페이지
const lastId = firstPage[firstPage.length - 1].id;
const secondPage = await getNextPage(lastId); // 커서로 다음 페이지

응답에 커서를 실어서 내려주는 API 형태

실무에서는 보통 이렇게 응답 형태에 nextCursor를 같이 내려준다.

1
2
3
4

12

async function getPostsCursor(cursor?: number) {
  const posts = await postRepository.find({
    where: cursor ? { id: LessThan(cursor) } : {},
    order: { id: 'DESC' },
    take: 10,
  });

  return {
    data: posts,
    nextCursor: posts.length > 0 ? posts[posts.length - 1].id : null,
  };
}

  "nextCursor": 82

클라이언트는 다음 요청을 보낼 때 nextCursor 값을 그대로 커서 파라미터로 넣어서 호출하면 된다.

정렬 기준이 여러 개일 때 (복합 커서)

id 하나만 정렬 기준이면 간단한데, 예를 들어 “좋아요 많은 순, 같으면 최신순”처럼 정렬 기준이 두 개면 커서도 두 값을 같이 써야 한다.

1
2
3
4
5
6

-- 정렬: likeCount DESC, id DESC
-- 마지막으로 받은 행이 (likeCount=50, id=91)이라면
SELECT * FROM posts
WHERE (likeCount < 50) OR (likeCount = 50 AND id < 91)
ORDER BY likeCount DESC, id DESC
LIMIT 10;

포인트는 “튜플 비교”라는 개념이다. likeCount가 같으면 그다음 기준(id)으로 비교해서 이어간다는 뜻을, OR로 풀어서 표현한 것. (MySQL 8.0+에서는 (likeCount, id) < (50, 91)처럼 튜플 비교 문법을 직접 쓸 수도 있다.)

1

// TypeORM에서는 QueryBuilder로 직접 조건을 만든다
const posts = await postRepository
  .createQueryBuilder('post')
  .where(
    '(post.likeCount < :likeCount) OR (post.likeCount = :likeCount AND post.id < :id)',
    { likeCount: 50, id: 91 }
  )
  .orderBy('post.likeCount', 'DESC')
  .addOrderBy('post.id', 'DESC')
  .take(10)
  .getMany();

어떤 걸 써야 하나

  OFFSET Cursor
뒤 페이지로 갈수록 성능 점점 느려짐 거의 일정
특정 페이지로 바로 점프 (예: 37페이지) 가능 불가능 (이전 결과의 다음만 알 수 있음)
데이터가 실시간으로 추가/삭제될 때 페이지 밀림/중복 발생 가능 영향 없음
잘 맞는 UI 페이지 번호 클릭 게시판 무한 스크롤 피드

페이지 번호를 직접 눌러 이동해야 하는 게시판이라면 커서로는 “37페이지”라는 개념 자체를 못 만들기 때문에 OFFSET이 필요하고, SNS 피드처럼 계속 이어서 불러오는 무한 스크롤이라면 커서 방식이 성능도 좋고 데이터 변화에도 안정적이다.

OFFSET은 왜 중간에 데이터가 바뀌면 밀리는가

게시글이 최신순으로 정렬돼 있고, 페이지당 3개씩 보여준다고 하자.

1페이지 요청 (OFFSET 0 LIMIT 3) — 이 시점 게시글: [10, 9, 8, 7, 6, 5, ...]

1

1페이지 결과: 10, 9, 8

그 사이에 새 글(id=11)이 올라온다 → 전체 목록이 [11, 10, 9, 8, 7, 6, 5, ...]로 바뀜

2페이지 요청 (OFFSET 3 LIMIT 3)

1

2페이지 결과: 8, 7, 6

8이 1페이지에서도 나왔는데 2페이지에도 또 나온다. OFFSET 3은 “맨 앞에서 3번째까지 건너뛰고”라는 뜻인데, 새 글이 하나 껴들어오면서 전체 순서가 한 칸씩 밀려서 원래 4번째였던 8이 다시 4번째 자리를 차지하게 된 것이다. (반대로 삭제가 일어나면, 이번엔 어떤 글을 아예 못 보고 건너뛰는 경우도 생긴다.)

같은 상황을 Cursor로 처리하면 다르다. 1페이지에서 마지막으로 받은 id=8을 커서로 그대로 들고 있다가, 그 값 기준으로 다음 페이지를 요청한다.

1
2
3

-- id=8 다음(더 작은 것)부터 3개 — 그 사이 새 글이 몇 개 생기든 이 조건은 그대로 유효함
SELECT * FROM posts WHERE id < 8 ORDER BY id DESC LIMIT 3;
-- 결과: 7, 6, 5 (중복도 누락도 없음)

OFFSET 3(몇 번째)이 아니라 id < 8(이 값보다 작은 것)로 찾기 때문에, 그 사이에 글이 몇 개 추가되든 상관없이 항상 정확히 “8 다음”부터 이어진다.

정리

  • OFFSET: 구현이 직관적이고 페이지 점프가 가능하지만, 뒤로 갈수록 앞부분을 읽고 버리는 비용 때문에 느려진다.
  • Cursor: 마지막으로 본 지점부터 이어서 읽기 때문에 몇 페이지를 가든 속도가 일정하지만, 페이지 점프는 불가능하다.
  • 정렬 기준이 여러 개면 커서도 여러 값을 같이 써서 “튜플 비교”로 이어간다.
  • 게시판형(페이지 점프 필요)엔 OFFSET, 무한 스크롤형(계속 이어보기)엔 Cursor가 기본 선택 기준이다.
