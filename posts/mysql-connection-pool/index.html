MySQL 커넥션 풀(Connection Pool)

DB 커넥션 풀이 필요한 이유와, 풀 크기를 잘못 잡았을 때 발생하는 Too many connections 문제를 정리한다.

게시 2026/08/25
By Sooyoung Choi
읽는 시간 4분

커넥션 풀이 왜 필요한가

매 요청마다 DB 커넥션을 새로 맺으면(TCP 연결 + 인증) 그 자체로 시간이 소요된다. 요청이 많아질수록 이 비용이 계속 반복되면서 낭비가 커진다.

그래서 애플리케이션이 시작할 때 커넥션을 미리 여러 개 만들어두고, 요청이 들어올 때마다 그중 하나를 빌려서 쓰고, 다 쓰면 반납하는 방식을 쓴다. 이게 커넥션 풀(Connection Pool)이다.

EX) TypeORM에서는 이렇게 풀 크기를 지정한다.

1
2
3

extra: {
  connectionLimit: 10,
}

풀 크기, 무작정 크게 잡으면 안 되는 이유

  • 풀 크기를 너무 작게 잡으면 → 동시 요청이 몰릴 때 빌릴 수 있는 커넥션이 없어서 커넥션 타임아웃이 난다.
  • 풀 크기를 너무 크게 잡으면 → MySQL 서버가 감당할 수 있는 최대 커넥션 수(max_connections)를 넘겨버릴 수 있다.

실제로 초과하면 무슨 일이 생기나

EX) 서버 인스턴스 3대, 각 인스턴스마다 connectionLimit: 100, MySQL max_connections: 200인 상황

  • 전체 커넥션 수요는 최대 3 × 100 = 300개인데, MySQL은 200개까지만 받아준다.
  • 200개를 넘는 순간부터 MySQL은 새로운 커넥션 시도 자체를 거부한다.
  • 그 시점 이후 커넥션을 맺으려는 서버들은 Too many connections 에러를 받는다.
  • 이 에러를 받은 요청들은 DB 작업을 시도조차 못 하고 그대로 실패한다. (쿼리가 느린 게 아니라, 애초에 연결 자체가 안 되는 것)

실무에서의 기준

핵심 공식은 이거다.

1

서버 인스턴스 수 × 인스턴스당 connectionLimit  <  MySQL max_connections

그냥 작기만 하면 되는 게 아니라, 여유 있게 작아야 한다. (다른 애플리케이션/관리 도구/모니터링 툴도 커넥션을 나눠 쓰기 때문)

EX) 서버 인스턴스 3대, MySQL max_connections: 200이라면 → 인스턴스당 connectionLimit은 5~60 정도가 적정선. (3대 × 60 = 180으로, 200에 딱 붙지 않고 여유를 남겨둔 값)

정리

  • 커넥션 풀은 매 요청마다 커넥션을 새로 맺는 비용(TCP + 인증)을 없애기 위해, 미리 만들어둔 커넥션을 빌려 쓰고 반납하는 방식이다.
  • 풀 크기는 작으면 타임아웃, 크면 MySQL의 max_connections 초과로 이어지므로 양쪽 다 조심해야 한다.
  • 여러 서버 인스턴스를 운영한다면, (인스턴스 수 × 인스턴스당 풀 크기)가 MySQL max_connections보다 여유 있게 작아야 Too many connections 에러를 피할 수 있다.
