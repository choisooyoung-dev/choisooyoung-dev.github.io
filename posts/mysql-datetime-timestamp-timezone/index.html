MySQL DATETIME vs TIMESTAMP, 그리고 타임존

DATETIME과 TIMESTAMP의 저장 방식·범위·타임존 처리 차이를 정리하고, 서버-DB 간 타임존이 다를 때 흔히 겪는 문제를 예제로 정리한다.

게시 2026/09/03
By Sooyoung Choi
읽는 시간 6분

날짜/시간 컬럼을 만들 때 DATETIME과 TIMESTAMP 중 뭘 써야 할지 헷갈릴 때가 많다. 둘 다 날짜와 시간을 저장하지만, 타임존을 다루는 방식이 근본적으로 다르다.

저장 방식의 차이

1
2
3
4
5

CREATE TABLE event (
  id INT PRIMARY KEY,
  started_at DATETIME,
  logged_at TIMESTAMP
);
  • DATETIME: 입력한 값을 그대로 저장한다. 타임존 개념이 없다. 2026-09-03 10:00:00을 넣으면 그 문자 그대로 저장되고, 그대로 조회된다.
  • TIMESTAMP: 저장할 때 세션의 time_zone 설정 기준으로 UTC로 변환해서 저장한다. 조회할 때는 다시 세션의 time_zone 기준으로 변환해서 보여준다. 즉 실제 저장값은 UTC, 보여주는 값은 현재 세션 타임존.

SET time_zone = '+09:00';
INSERT INTO event (started_at, logged_at) VALUES ('2026-09-03 10:00:00', '2026-09-03 10:00:00');

SET time_zone = '+00:00';
SELECT started_at, logged_at FROM event;
-- started_at: 2026-09-03 10:00:00  (그대로, 타임존 영향 없음)
-- logged_at : 2026-09-03 01:00:00  (UTC로 환산돼서 보임)

같은 순간을 가리키더라도, 세션의 time_zone이 바뀌면 TIMESTAMP는 화면에 찍히는 값이 달라진다. DATETIME은 절대 안 바뀐다.

범위와 용량 차이

  DATETIME TIMESTAMP
범위 1000-01-01 ~ 9999-12-31 1970-01-01 ~ 2038-01-19 (UTC 기준)
저장 용량 8바이트 (5.6.4 이후 5바이트 + fsp) 4바이트
타임존 인식 없음 있음 (UTC로 변환 저장)
기본값 자동 갱신 직접 지정 필요 DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP 편하게 사용

TIMESTAMP는 4바이트 정수(유닉스 타임)로 저장되기 때문에 2038년 문제를 그대로 물려받는다. 그 이후 날짜를 다뤄야 하면 DATETIME을 써야 한다.

언제 뭘 쓸까

  • 서버가 여러 타임존에 걸쳐 있거나, 사용자마다 다른 타임존으로 시간을 보여줘야 하는 경우 → TIMESTAMP. UTC로 저장해두면 조회 시점의 세션 타임존에 맞게 자동으로 변환된다.
  • 특정 시각 자체가 의미 있고, 타임존과 무관하게 고정돼야 하는 경우 (ex. “매일 자정에 배치 실행” 같은 로컬 시각, 생년월일) → DATETIME. 타임존 변환으로 값이 흔들리면 안 되는 데이터.
  • 2038년 이후를 다뤄야 하는 경우 → 무조건 DATETIME.

실무에서 자주 겪는 문제

애플리케이션 서버 타임존과 DB(또는 커넥션 세션) 타임존이 다를 때 사고가 난다.

1
2

-- 서버는 UTC로 시각을 만들어 보내는데, DB 세션 time_zone이 KST(+09:00)라면
-- TIMESTAMP 컬럼에 "그 순간"이 아니라 "표시 시각 기준"으로 9시간 밀려서 저장/조회될 수 있다.
  • Node.js/TypeORM 등에서 커넥션을 맺을 때 timezone 옵션을 명시적으로 맞추지 않으면, 서버 로컬 시간과 DB 세션 시간이 어긋난 채로 TIMESTAMP 변환이 일어난다.
  • 가장 안전한 방식은 DB 세션 타임존을 항상 UTC로 고정하고, 애플리케이션(백엔드)에서 필요한 시점에만 사용자 타임존으로 변환해서 보여주는 것. 저장은 항상 UTC 하나로 통일하면 여러 타임존이 섞여도 꼬일 일이 없다.
  • DATETIME을 쓰더라도 “이 값은 어느 타임존 기준인지”를 암묵적으로 정해두지 않으면 똑같이 문제가 생긴다. 컬럼에 타임존 정보가 없으므로, 저장하기 전에 애플리케이션 레벨에서 UTC로 변환해서 넣는 규칙이 필요하다.

정리

  • DATETIME은 입력값을 그대로 저장·조회하는 타임존 비인식(naive) 타입, TIMESTAMP는 저장 시 UTC로 변환하고 조회 시 세션 타임존으로 다시 변환하는 타임존 인식 타입이다.
  • TIMESTAMP는 2038년까지만 표현 가능하고 4바이트로 더 가볍다. DATETIME은 훨씬 넓은 범위를 4바이트보다 더 쓰지만 표현할 수 있다.
  • 여러 타임존을 다뤄야 하면 TIMESTAMP + DB 세션 UTC 고정, 특정 로컬 시각 자체가 고정값으로 의미 있으면 DATETIME.
  • 어느 쪽을 쓰든 저장은 UTC로 통일하고, 사용자에게 보여줄 때만 타임존을 변환하는 게 사고를 가장 줄이는 방식이다.
