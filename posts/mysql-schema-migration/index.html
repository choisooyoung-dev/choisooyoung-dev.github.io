스키마 마이그레이션 관리

스키마 변경을 코드로 관리해야 하는 이유, 마이그레이션 도구의 동작 방식, 무중단으로 컬럼을 안전하게 바꾸는 절차를 정리한다.

게시 2026/09/03
By Sooyoung Choi
읽는 시간 7분

ALTER TABLE을 로컬 DB나 운영 DB에 직접 실행해서 스키마를 바꾸면, 어떤 서버가 어떤 스키마를 가지고 있는지 금방 어긋난다. 마이그레이션 도구로 스키마 변경을 코드처럼 버전 관리해야 하는 이유와, 운영 환경에서 안전하게 바꾸는 방법을 정리한다.

왜 직접 ALTER 하면 안 되는가

  • 로컬/스테이징/운영 DB에 각각 수동으로 ALTER TABLE을 실행하면, 어느 환경에 어떤 변경이 적용됐는지 추적이 안 된다. 새로 합류한 팀원의 로컬 DB는 운영과 다른 스키마를 가지고 있을 수 있다.
  • 배포와 스키마 변경 순서가 맞물리지 않으면, 새 코드가 아직 없는 컬럼을 참조하거나 옛 코드가 이미 사라진 컬럼을 참조해서 장애가 난다.
  • 마이그레이션 도구는 이 변경들을 순서가 있는 파일(버전) 로 관리해서, “지금 DB가 몇 번째 마이그레이션까지 적용됐는지”를 DB 자체에 기록해두고 추적한다.

// TypeORM 마이그레이션 예시
export class AddCouponExpiredAt1693737600000 implements MigrationInterface {
  async up(queryRunner: QueryRunner): Promise<void> {
    await queryRunner.query(`ALTER TABLE coupon ADD COLUMN expired_at DATETIME NULL`);
  }

  async down(queryRunner: QueryRunner): Promise<void> {
    await queryRunner.query(`ALTER TABLE coupon DROP COLUMN expired_at`);
  }
}
  • 각 마이그레이션 파일은 up(적용)과 down(되돌리기) 을 한 쌍으로 가진다. 배포 후 문제가 생기면 down으로 롤백할 수 있어야 한다.
  • DB에는 migrations라는 별도 테이블이 생겨서, 어떤 마이그레이션까지 실행됐는지 이름/타임스탬프로 기록한다. 배포 시 이 테이블을 보고 아직 실행 안 된 마이그레이션만 순서대로 적용한다.
  • 이렇게 하면 로컬이든 운영이든 “마이그레이션을 끝까지 실행”하면 항상 같은 스키마 상태가 보장된다 — Git 커밋 히스토리처럼 스키마도 버전 관리되는 셈.

무중단으로 컬럼 변경하기

문제는 운영 DB에서 큰 테이블에 ALTER TABLE을 실행할 때다. 예를 들어 컬럼 타입을 바꾸거나 NOT NULL 제약을 추가하면, 테이블 전체를 다시 쓰는 작업이라 오래 걸리고 그 사이 락이 걸려 서비스가 멈출 수 있다.

안전하지 않은 방식 (한 번에 처리)

1
2

-- 컬럼 타입을 한 번에 바꾸면, 대용량 테이블에서 긴 락이 걸릴 수 있다
ALTER TABLE orders MODIFY COLUMN status VARCHAR(50) NOT NULL;

단계적으로 나누는 방식 (Expand-Contract)

배포 시점이 다른 여러 단계로 나눠서, 매 배포마다 이전 버전 코드와 새 버전 코드가 동시에 존재해도 깨지지 않게 만든다.

  1. Expand: 기존 컬럼은 그대로 둔 채 새 컬럼을 nullable로 추가한다. (ALTER TABLE orders ADD COLUMN status_v2 VARCHAR(50) NULL)
  2. Dual write: 애플리케이션 코드를 배포해서 새 데이터는 두 컬럼 모두에 쓰도록 한다. 기존 코드도 옛 컬럼만 보고 있으니 문제없이 동작한다.
  3. Backfill: 배치 작업으로 기존 row들의 값을 새 컬럼에도 채워 넣는다. 벌크 UPDATE로 조금씩 나눠서 처리해 락 경합을 줄인다.
  4. Switch read: 애플리케이션이 새 컬럼을 읽도록 배포를 바꾼다. 이 시점부터 옛 컬럼은 안 읽히지만 계속 쓰기는 유지.
  5. Contract: 문제없음을 확인한 뒤, 옛 컬럼 쓰기를 멈추고 컬럼을 삭제한다.

한 번의 ALTER로 끝내지 않고 이렇게 나누는 이유는, 배포 도중 잠깐이라도 새 코드와 옛 코드가 동시에 떠 있는 순간(롤링 배포, 여러 인스턴스)에도 양쪽 다 정상 동작해야 하기 때문이다.

그 밖의 안전장치

  • pt-online-schema-change, gh-ost 같은 온라인 DDL 도구: 원본 테이블은 그대로 두고 새 스키마의 임시 테이블을 만들어 데이터를 복사한 뒤, 완료되면 테이블을 교체하는 방식으로 락 시간을 최소화한다. 대용량 테이블의 ALTER엔 거의 필수.
  • 마이그레이션은 되도록 작게, 되돌릴 수 있게(down 검증) 작성한다. 큰 변경을 한 마이그레이션에 몰아넣으면 실패했을 때 롤백 범위도 커진다.
  • 운영에 반영하기 전 스테이징 환경에서 실제 데이터 볼륨과 비슷한 규모로 미리 실행해서 소요 시간과 락 영향을 가늠해본다.

정리

  • 스키마 변경은 수동 ALTER가 아니라 마이그레이션 파일(버전 + up/down) 로 관리해서, 모든 환경의 스키마 상태를 일치시킨다.
  • 대용량 테이블의 파괴적인 변경은 한 번에 하지 않고 Expand → Dual write → Backfill → Switch → Contract 단계로 나눠서, 배포 중에도 신구 코드가 공존할 수 있게 한다.
  • 락 시간이 걱정되는 대용량 테이블은 gh-ost, pt-online-schema-change 같은 온라인 DDL 도구를 고려한다.
