LIKE 검색과 인덱스 한계, 그리고 FULLTEXT 인덱스

LIKE 검색이 인덱스를 타는 경우와 못 타는 경우를 B+Tree 관점에서 정리하고, 포함 검색 대안인 FULLTEXT 인덱스 사용법을 정리한다.

게시 2026/08/31
By Sooyoung Choi
읽는 시간 9분

LIKE는 항상 인덱스를 못 타는 게 아니다

와일드카드(%)가 어디 붙어있느냐에 따라 갈린다.

1
2
3
4
5
6

-- 인덱스 탐 (Prefix 매칭)
SELECT * FROM users WHERE name LIKE '김%';

-- 인덱스 못 탐 (앞에 % 붙음)
SELECT * FROM users WHERE name LIKE '%수%';
SELECT * FROM users WHERE name LIKE '%수';

왜 이런 차이가 생기나 — B+Tree 관점

B+Tree 글에서 봤듯이, 인덱스는 값이 정렬된 상태로 저장돼 있다. name 인덱스라면 가나, 가온, 김철수, 나영희… 이렇게 사전순으로 쭉 정렬돼 있는 것이다.

  • LIKE '김%': “김”으로 시작하는 값들은 정렬된 순서상 한 구간에 모여 있다. 김이 시작되는 지점을 찾아서, 김으로 시작하는 동안만 쭉 읽으면 된다 → range 스캔 가능 (EXPLAIN type의 range)
  • LIKE '%수%': “수”가 어디에 들어있는지는 정렬 순서와 아무 상관이 없다. 김철수도 있고 수영장도 있고 영수증도 있는데, 이것들은 정렬 순서상 전혀 다른 위치에 흩어져 있다. 정렬을 이용해서 구간을 좁히는 게 불가능해서, 인덱스가 있어도 결국 전체를 다 봐야 한다 (type: ALL).

EXPLAIN으로 확인

1
2
3
4
5

EXPLAIN SELECT * FROM users WHERE name LIKE '김%';
-- type: range

EXPLAIN SELECT * FROM users WHERE name LIKE '%수%';
-- type: ALL (인덱스가 있어도 안 씀!)

검색 기능(게시글 제목/본문에서 키워드 찾기 등)에 LIKE '%키워드%'를 쓰면, 데이터가 많아질수록 무조건 느려진다. 데이터 몇백 건일 땐 안 느껴지다가, 몇십만 건이 되면 바로 체감된다.

대안 1: FULLTEXT 인덱스

MySQL이 자체 제공하는 전문 검색(제목/본문 전체를 대상으로 하는 검색) 기능. 단어 단위로 미리 인덱싱해둬서, “포함 검색”도 인덱스로 처리할 수 있게 해준다.

인덱스 생성

1
2
3
4
5
6

CREATE TABLE posts (
  id INT PRIMARY KEY,
  title VARCHAR(255),
  content TEXT,
  FULLTEXT INDEX ft_content (title, content) -- title, content 묶어서 전문 인덱스
);

검색 — MATCH ... AGAINST

1
2
3
4
5
6

-- 자연어 모드(기본): "MySQL"이 포함된 글을 관련도순으로
SELECT id, title,
  MATCH(title, content) AGAINST('MySQL') AS relevance
FROM posts
WHERE MATCH(title, content) AGAINST('MySQL')
ORDER BY relevance DESC;

1
2

EXPLAIN SELECT * FROM posts WHERE MATCH(title, content) AGAINST('MySQL');
-- type: fulltext ← 인덱스를 제대로 탐!

LIKE '%MySQL%'이었다면 type: ALL이었을 게, FULLTEXT 인덱스 덕분에 type: fulltext로 바뀐다. 미리 단어 단위로 쪼개서(형태소 분석 등) 인덱싱해두기 때문에, “포함 검색”인데도 인덱스를 탈 수 있는 것이다.

Boolean 모드 — AND/OR/제외 조건

1
2
3

-- "mysql"은 포함하고 "mariadb"는 제외
SELECT * FROM posts
WHERE MATCH(title, content) AGAINST('+mysql -mariadb' IN BOOLEAN MODE);
  • +단어: 반드시 포함
  • -단어: 반드시 제외
  • "정확한 문구": 구문 그대로 검색

TypeORM에서 쓰기

TypeORM은 MATCH AGAINST를 직접 지원하는 헬퍼가 없어서, QueryBuilder의 where에 직접 써야 한다.

1
2
3
4
5
6
7

const posts = await postRepository
  .createQueryBuilder('post')
  .where(
    'MATCH(post.title, post.content) AGAINST(:keyword IN NATURAL LANGUAGE MODE)',
    { keyword: 'MySQL' }
  )
  .getMany();

한글 검색 품질 — ngram 파서

한글은 기본 파서로는 형태소 분석이 약해서 (예: “먹었어요”로 검색해도 “먹다”로 매칭이 잘 안 될 수 있음), 품질을 높이려면 ngram 파서를 쓴다.

기본 파서는 공백이나 특수문자를 기준으로 단어 단위로 쪼갠다. 영어는 이게 잘 맞지만(I love MySQL → I, love, MySQL), 한글은 띄어쓰기 단위가 실제 의미 단위랑 잘 안 맞는다.

EX) “마이SQL을 공부했다”를 기본 파서로 쪼개면 → 마이SQL을, 공부했다 (조사까지 붙어서 통째로 하나의 단어 취급). 나중에 “마이SQL”로 검색해도 “마이SQL을”이라는 통짜 단어와 정확히 일치하지 않아서 검색이 안 될 수 있다.

ngram 파서는 의미 단위를 신경 쓰지 않고, 그냥 n글자씩 겹쳐가며 자른다. 기본값은 2글자(bigram)다.

EX) “마이SQL을”을 2-gram으로 쪼개면 → 마이, 이S, SQ, QL, L을 처럼 2글자씩, 한 칸씩 밀면서 겹치게 잘라 각각을 인덱싱한다.

검색어 “마이SQL”도 똑같이 2글자씩 쪼개면 마이, 이S, SQ, QL이 나온다. 이 조각들이 원본 텍스트를 쪼갠 조각들 안에 다 포함되어 있으므로, 조사가 붙든 안 붙든 정확한 “단어”가 아니어도 부분적으로 겹치기만 하면 찾아낼 수 있다. 즉 기본 파서는 “완전한 단어가 일치해야” 찾고, ngram 파서는 “짧은 조각들이 겹치기만 해도” 찾을 수 있어서, 조사가 붙거나 띄어쓰기가 애매한 한글 검색에 더 잘 맞는다.

-- ngram 파서 사용 + 몇 글자 단위로 쪼갤지 지정 (기본 2)
SET GLOBAL ngram_token_size = 2;

CREATE TABLE posts (
  ...
  FULLTEXT INDEX ft_content (title, content) WITH PARSER ngram
);

ngram_token_size를 크게 하면(예: 3글자) 정확도는 조금 올라가지만, 그만큼 인덱스 크기와 검색 범위가 커져서 무거워진다. 한글은 보통 2글자가 흔히 쓰이는 기본값이다.

대안 2: 검색 전용 엔진 (Elasticsearch 등)

검색 기능이 서비스의 핵심 기능이라면, 아예 MySQL 밖으로 검색을 빼서 전문 검색 엔진에 맡기는 방식. 형태소 분석, 오타 허용, 가중치 기반 랭킹 등 FULLTEXT보다 훨씬 강력한 검색 기능을 제공한다. 실무에서 텍스트 검색이 핵심인 서비스(쇼핑몰 상품 검색, 콘텐츠 검색 등)는 거의 이 방식을 쓴다. 대신 MySQL과 별도로 데이터를 동기화해야 하는 복잡도가 늘어난다.

정리

  • LIKE '키워드%'(접두사 검색)는 인덱스의 정렬 순서를 이용할 수 있어서 range로 처리된다.
  • LIKE '%키워드%'(포함 검색)는 정렬 순서와 무관해서 인덱스가 있어도 전체 스캔(ALL)이 된다.
  • 포함 검색이 필요하면 MySQL의 FULLTEXT 인덱스(MATCH ... AGAINST)를 쓰거나, 검색이 핵심 기능이면 Elasticsearch 같은 전용 검색 엔진으로 분리한다.
  • 한글 검색 품질이 중요하면 FULLTEXT에 ngram 파서를 함께 고려한다.
