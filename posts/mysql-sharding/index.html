MySQL 샤딩(Sharding) - 여러 대의 DB 서버로 데이터 분산시키기

샤딩의 개념과 복제와의 차이, 샤딩 키 선택과 핫스팟 문제, 크로스 샤드 JOIN·분산 트랜잭션·리샤딩의 어려움을 정리한다.

게시 2026/08/31
By Sooyoung Choi
읽는 시간 10분

파티셔닝이 한 서버 안에서 테이블을 쪼갠 거라면, 샤딩은 여러 대의 DB 서버로 데이터 자체를 분산시키는 것이다.

샤딩이란

다른 데이터를 여러 서버에 나눠 담는 것. 데이터 양 자체가 한 대의 DB로는 감당이 안 될 만큼 커졌을 때 쓴다.

EX) 유저가 수억 명이라 users, orders 테이블이 너무 커졌다면 → user_id % 4 값으로 4대의 DB 서버(shard-0 ~ shard-3)에 유저 데이터를 나눠 담는다.

  • user_id = 101 → 101 % 4 = 1 → shard-1에 저장
  • user_id = 102 → 102 % 4 = 2 → shard-2에 저장

이러면 각 서버는 전체 데이터의 1/4만 갖고 있으면 된다.

복제(Replication)와 다르다

헷갈리기 쉬운데 목적 자체가 다르다.

  복제 (Replication) 샤딩 (Sharding)
데이터 같은 데이터를 여러 대에 복사 다른 데이터를 여러 대에 나눠 담음
목적 읽기 부하 분산 (Read Replica) 데이터 양 자체를 분산 (용량 한계 돌파)
한 서버 장애 시 다른 서버가 같은 데이터를 갖고 있어서 대체 가능 그 샤드의 데이터만 못 씀 (전체 중 일부만 영향)

복제 글에서 다뤘던 Master-Slave는 “같은 데이터를 여러 벌 복사해서 읽기를 분산”하는 거고, 샤딩은 “애초에 데이터를 쪼개서 서로 다른 서버에 나눠 담는” 거라 완전히 다른 문제를 푼다. 실무에서는 둘을 같이 쓰기도 한다 (샤드마다 각각 Read Replica를 둘 수도 있음).

샤딩 키 선택이 관건

어떤 컬럼 값을 기준으로 데이터를 나눌지(샤딩 키)가 샤딩의 성패를 가른다.

user_id를 샤딩 키로 잡으면, “이 유저와 관련된 쿼리는 어느 샤드로 가야 할지” 계산 한 번으로 바로 알 수 있어서 효율적이다.

1

shard_index = user_id % 샤드_개수

키를 잘못 고르면 생기는 문제: 핫스팟(Hotspot)

샤딩 키를 잘못 고르면, 특정 샤드에만 데이터와 트래픽이 몰리는 핫스팟 문제가 생긴다.

EX) 샤딩 키를 signup_date(가입일)로 잡았다고 하면 → 최근에 가입한 유저일수록 활동이 많은데, “최근 가입자”는 전부 같은(가장 최신) 샤드에 몰려 있다. → 그 샤드만 트래픽이 폭주하고, 오래된 유저가 담긴 다른 샤드들은 한가하다. → 샤드를 여러 대로 늘린 의미가 없어진다 (분산의 목적 상실).

그래서 보통 user_id처럼 값이 고르게 분포하고, 특정 값에 트래픽이 쏠리지 않는 컬럼을 샤딩 키로 고른다.

샤딩이 어려운 이유

1. 크로스 샤드 JOIN (Cross-shard JOIN)

서로 다른 DB 서버에 있는 데이터는 SQL의 JOIN으로 한 번에 못 묶는다. 각 샤드에서 따로 조회한 다음, 애플리케이션 코드에서 직접 합쳐야 한다.

EX) “유저 A와 유저 B가 같이 참여한 주문”을 조회한다면?

  • 유저 A는 shard-1에, 유저 B는 shard-3에 있을 수 있음
  • shard-1에서 A의 주문 목록 조회, shard-3에서 B의 주문 목록 조회 → 각각 따로 쿼리
  • 두 결과를 애플리케이션 코드(예: JS의 Array.filter/Map)로 직접 매칭해서 합침

한 서버 안에서라면 JOIN orders o ON ... 한 줄이면 끝날 일이, 샤딩 환경에서는 쿼리 2번 + 애플리케이션 레벨 병합 로직이 필요해진다.

2. 트랜잭션

두 샤드에 걸친 데이터를 원자적으로(ACID) 처리하려면, 단일 서버의 BEGIN ~ COMMIT 트랜잭션으로는 안 된다. 2PC(Two-Phase Commit) 같은 훨씬 복잡한 분산 트랜잭션이 필요해진다.

EX) 유저 A(shard-1)의 포인트를 차감하고 유저 B(shard-3)에게 적립하는 “포인트 이체”를 한다면 → shard-1에서의 차감과 shard-3에서의 적립이 둘 다 성공하거나 둘 다 실패해야 하는데, 서로 다른 DB라 하나의 트랜잭션으로 묶을 수가 없다. 한쪽만 성공하고 다른 쪽이 실패하면 데이터가 어긋난다.

3. 리샤딩(Re-sharding)

나중에 샤드를 늘리거나 재분배해야 할 때, 이미 나뉜 데이터를 다시 옮기는 작업이 필요한데 이게 굉장히 크고 위험하다.

EX) 샤드를 4대 → 8대로 늘리면 → user_id % 4로 계산했던 기존 샤드 배치가 user_id % 8 기준으로는 전부 재계산돼서 위치가 바뀐다.

  • 기존: user_id = 5 → 5 % 4 = 1 → shard-1
  • 변경 후: user_id = 5 → 5 % 8 = 5 → shard-5

거의 모든 데이터를 다른 서버로 옮겨야 하는 대규모 마이그레이션이 발생한다. 서비스 운영 중에 데이터 정합성을 유지하면서 옮기는 건 실무에서 가장 부담스러운 작업 중 하나다. (이런 문제 때문에 처음부터 나누기 쉬운 방식, 예를 들어 고정 개수보다 훨씬 많은 논리 샤드를 만들고 물리 서버에는 여러 논리 샤드를 묶어서 배치하는 방식(consistent hashing 등)을 쓰기도 한다.)

실무에서는 최후의 수단

단일 DB 서버로 감당이 안 될 때만 샤딩을 도입한다. 그 전에는 아래 조합으로 최대한 버틴다.

  • 복제(Replication): 읽기 트래픽을 Read Replica로 분산
  • 파티셔닝: 한 서버 안에서 테이블을 쪼개 조회 범위를 줄임
  • 캐싱: 자주 조회되는 데이터를 DB 앞단(Redis 등)에서 미리 처리해서 DB까지 안 가게 함

EX) 상품 상세 페이지 조회 → 매번 DB에서 상품 정보를 읽는 대신, Redis에 product:1234 형태로 캐싱해두고 캐시에 있으면 DB를 아예 안 거친다. 캐시가 없을 때만(cache miss) DB를 조회하고, 그 결과를 다시 캐시에 저장한다. 이러면 실제 DB로 가는 요청 자체가 크게 줄어든다.

샤딩은 한 번 도입하면 되돌리기 어렵고, 크로스 샤드 JOIN·분산 트랜잭션·리샤딩 문제로 시스템 복잡도가 확 늘어나는 선택이다. 그래서 “데이터 양 자체가 진짜로 한계에 부딪혔을 때”의 최후 수단으로 접근하는 게 일반적이다.

정리

  • 샤딩은 다른 데이터를 여러 서버에 나눠 담는 것 (복제는 같은 데이터를 복사하는 것 — 목적이 다름).
  • 샤딩 키를 잘못 고르면 특정 샤드에 트래픽이 몰리는 핫스팟 문제가 생긴다.
  • 크로스 샤드 JOIN, 분산 트랜잭션, 리샤딩이 샤딩을 어렵게 만드는 3대 요인이다.
  • 복제 + 파티셔닝 + 캐싱으로 버틸 수 있는 만큼 버티고, 정말 데이터 양이 한계에 부딪혔을 때만 샤딩을 최후 수단으로 도입한다.
