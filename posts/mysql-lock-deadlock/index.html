MySQL 락(Lock)과 데드락(Deadlock)

MySQL Row Lock의 동작 방식과 데드락(Deadlock) 발생 과정, 실무 예방법을 예제 쿼리로 정리한다.

게시 2026/08/25
By Sooyoung Choi
읽는 시간 5분

앞서 ACID 격리 수준 글에서 “읽기 일관성은 격리 수준이, 쓰기 순서는 락(Lock)이 담당한다”고 정리했다. 이번엔 그 락을 직접 걸어보고, 락 때문에 생기는 데드락까지 정리한다.

락(Lock) → Row Lock

1
2
3
4

BEGIN;
SELECT qty FROM coupon WHERE id = 1 FOR UPDATE; -- 락 걸림!
UPDATE coupon SET qty = qty - 1 WHERE id = 1;
COMMIT; -- 락 풀림!
  • SELECT ... FOR UPDATE는 조회하면서 동시에 해당 row에 쓰기 락(exclusive lock)을 건다.
  • InnoDB는 Row(행) 단위 락이라서, 다른 트랜잭션이 같은 row를 건드리려고 하면 앞 트랜잭션이 COMMIT(또는 ROLLBACK)해서 락이 풀릴 때까지 기다린다.
  • 반면 해당 테이블의 다른 row는 전혀 영향받지 않아서 동시에 처리 가능하다.

이게 MyISAM의 테이블 락과 다른 결정적인 차이다. MyISAM은 행 하나만 바꿔도 테이블 전체가 잠기지만, InnoDB의 row lock은 딱 그 row만 잠근다.

데드락 (Deadlock)

서로 다른 두 트랜잭션이 서로가 가진 락을 기다리며 영원히 멈추는 상황.

-- 트랜잭션 A
BEGIN;
UPDATE coupon SET remaining = remaining - 1 WHERE id = 1; -- id=1 락 잡음
-- 잠시 후
UPDATE coupon SET remaining = remaining - 1 WHERE id = 2; -- id=2 락 필요!

-- 트랜잭션 B
BEGIN;
UPDATE coupon SET remaining = remaining - 1 WHERE id = 2; -- id=2 락 잡음
-- 잠시 후
UPDATE coupon SET remaining = remaining - 1 WHERE id = 1; -- id=1 락 필요!

무슨 일이 벌어지는가

  1. 트랜잭션 A는 id=1을 잡고, id=2를 요청한다.
  2. 트랜잭션 B는 id=2를 잡고, id=1을 요청한다.
  3. 트랜잭션 A는 B가 id=2를 커밋해서 락을 풀 때까지 대기한다.
  4. 트랜잭션 B는 A가 id=1을 커밋해서 락을 풀 때까지 대기한다.
  5. 서로가 서로를 기다리므로 둘 다 영원히 대기 → 데드락.

핵심은, 두 트랜잭션이 같은 자원(id=1, id=2)을 서로 다른 순서로 건드렸다는 것. A는 1→2 순서로, B는 2→1 순서로 접근했기 때문에 이런 교착 상태가 만들어진다.

실제로는 MySQL(InnoDB)이 데드락을 감지하면, 둘 중 하나(보통 변경량이 적은 쪽)를 강제로 롤백시켜서 나머지 하나는 진행되게 한다. 그래도 롤백당한 쪽은 애플리케이션에서 재시도 로직이 필요하다.

실무 예방법

여러 row를 건드릴 땐 항상 같은 순서로 접근한다.

  • A, B 둘 다 id 오름차순으로 접근했다면, 하나가 먼저 두 락을 다 잡고 끝낼 때까지 다른 하나는 처음(id=1)부터 기다리기만 할 뿐 서로 물고 물리는 상황 자체가 생기지 않는다.
  • 그 외 방법: 트랜잭션을 짧게 유지하기, 락이 필요한 순서를 애플리케이션 레벨에서 통일하기, 필요 이상으로 넓은 범위를 잠그지 않기.

정리

  • InnoDB의 락은 Row 단위라서 MyISAM의 테이블 락보다 동시성이 훨씬 좋다.
  • SELECT ... FOR UPDATE로 명시적으로 쓰기 락을 걸 수 있고, 트랜잭션이 끝나야(COMMIT/ROLLBACK) 풀린다.
  • 데드락은 서로 다른 트랜잭션이 같은 자원을 서로 다른 순서로 잠글 때 발생한다.
  • 예방법은 간단하다 — 여러 row에 접근할 때 항상 같은 순서로 접근하기.
