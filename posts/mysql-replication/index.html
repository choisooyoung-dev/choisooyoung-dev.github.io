MySQL 복제(Replication)와 Read Replica

MySQL Master-Slave 복제 구조와 binlog, 복제 지연(Replication Lag) 문제와 해결 방법을 정리한다.

게시 2026/08/25
By Sooyoung Choi
읽는 시간 10분

복제(Replication)란

MySQL은 Master(원본)에 데이터를 쓰고, 그 변경 내역을 하나 이상의 Slave(복제본)로 실시간 복사하는 구조로 구성할 수 있다. 이렇게 Master의 변경사항을 받아 따라가는 Slave 서버를 Read Replica라고 부른다.

2
3

                 write                         read
Client ────────────────▶ Master ── binlog ──▶ Slave ◀──────────── Client
                                     복제
  • Master는 데이터가 변경될 때마다 그 내용을 binlog(binary log)라는 로그에 기록한다.
  • Slave는 이 binlog를 계속 받아와서, 자기 데이터에 똑같이 재생(replay)한다.
  • 이 과정이 반복되며 Slave는 Master를 실시간(에 가깝게) 따라가게 된다.

binlog(Binary Log)란

MySQL이 데이터를 변경하는 모든 작업(INSERT/UPDATE/DELETE, 테이블 구조 변경 등)을 순서대로 기록해두는 로그 파일. 역할은 크게 두 가지다.

  1. 복제: Master가 binlog에 남긴 변경 내역을 Slave가 읽어와서 그대로 재생 → Master/Slave가 같은 데이터를 유지
  2. 장애 복구(Point-in-Time Recovery): 특정 시점의 백업 + 그 이후의 binlog를 재생하면, 장애 발생 직전 시점까지 데이터를 복구할 수 있다

ACID 지속성(Durability)에 나온 redo log와 헷갈리기 쉬운데, 역할이 다르다.

  redo log binlog
목적 장애 복구 (서버가 죽었을 때 커밋된 데이터 복구) 복제 + 시점 복구
관리 주체 InnoDB 엔진 자체 MySQL 서버 레벨 (엔진 무관)
내용 물리적 변경 (디스크 페이지 단위) 논리적 변경 (실행된 SQL/row 변경 내용)

간단히: redo log는 “이 서버가 죽어도 복구되게” 하는 용도, binlog는 “다른 서버(Slave)한테 내가 뭘 바꿨는지 알려주는” 용도다.

읽기/쓰기 분산 (Read/Write Splitting)

보통 이렇게 트래픽을 나눈다.

  • 쓰기(INSERT/UPDATE/DELETE) → Master
  • 읽기(SELECT) → Slave

한 대의 DB가 모든 트래픽을 받는 대신, 읽기 트래픽을 여러 Slave로 분산시켜서 DB 전체 부하를 줄이고 읽기 처리량(throughput)을 늘리는 게 목적이다. 서비스는 보통 쓰기보다 읽기가 훨씬 많기 때문에 효과가 크다.

문제: 복제 지연 (Replication Lag)

Master에서 Slave로 데이터가 복제되는 데는 약간의 시간차가 있다. 네트워크, Slave의 처리 속도, 트래픽량에 따라 이 지연은 수 ms ~ 수 초까지 벌어질 수 있다.

EX) 사용자가 프로필을 수정(Master에 UPDATE) → 바로 그 프로필을 다시 조회(Slave에서 SELECT)

만약 그 조회 시점에 아직 복제가 안 끝났다면, 방금 수정한 내용이 반영 안 된 옛날 값을 보게 된다.

이걸 복제 지연 문제(Replication Lag)라고 한다. 특히 아래 같은 경우 문제가 커진다.

  • Slave에서 읽은 값을 그대로 다시 쓰기에 사용하는 경우: 옛날 값을 기준으로 로직을 태워서 잘못된 값이 들어갈 수 있다.
  • 방금 변경한 값을 사용자에게 바로 보여줘야 하는 경우 (내가 쓴 글이 바로 안 보이는 등): 사용자 입장에서 “방금 한 게 반영 안 됐다”는 버그처럼 느껴진다.

해결 방법

상황 해결책
방금 쓴 데이터를 바로 다시 읽어야 함 (read-after-write) 그 요청은 Slave가 아니라 Master에서 읽는다.
지연이 있어도 큰 문제 없는 조회 Slave에서 읽어도 무방. (통계, 대시보드, 목록 조회 등 “최신성”이 크리티컬하지 않은 경우)
서비스 전반적으로 지연에 민감함 Semi-sync replication을 고려 — Master가 커밋을 완료하기 전에 최소 1개 Slave가 로그를 받았는지 확인하고 커밋하는 방식. (완전한 동기식보다는 빠르고, 완전 비동기보다는 지연이 적음)
복제 지연 자체를 모니터링해야 함 SHOW REPLICA STATUS의 Seconds_Behind_Master 값으로 현재 지연 시간을 확인할 수 있다.

정리하면 “이 조회가 최신 데이터여야만 하는가?” 를 기준으로 Master/Slave를 선택하는 게 핵심이다. 무조건 Slave로 몰아서 부하를 줄이는 것도, 무조건 Master로만 읽는 것도 정답이 아니고, 데이터 최신성이 중요한 요청만 선택적으로 Master로 보내는 것이 일반적인 전략이다.

복제 방식: 비동기 vs 반동기(Semi-sync) vs 동기

Master가 Slave에게 변경 내역을 넘길 때, 얼마나 확실하게 확인하고 커밋할지에 따라 세 가지로 나뉜다.

방식 동작 특징
비동기 (Async) Master는 커밋하고 바로 응답. Slave에 전달됐는지는 신경 쓰지 않음 제일 빠름. 대신 Master가 죽으면 아직 전달 안 된 데이터는 유실될 수 있음. MySQL 기본값
반동기 (Semi-sync) Master가 커밋을 확정하기 전에, 최소 1개 Slave가 binlog를 받았다는 응답을 기다렸다가 커밋 완료 비동기보다 느리지만(네트워크 왕복 1번 추가), 완전 동기보다는 빠름
동기 (Sync) 모든 Slave가 완전히 반영(replay)까지 끝낼 때까지 기다림 제일 안전하지만 제일 느림. 실무에서 거의 안 씀

Semi-sync의 핵심은 “적어도 한 곳은 binlog를 확실히 받았다”는 것만 보장한다는 점이다. Slave가 그 로그를 실제로 데이터에 반영(replay)했는지까지는 보장하지 않고, 전달받았는지만 확인한다.

  • 장점: Master가 갑자기 죽어도, 최소 1개 Slave는 최신 binlog를 갖고 있으므로 비동기 방식보다 데이터 유실 가능성이 훨씬 낮다.
  • 단점: 그 확인을 기다리는 시간만큼 커밋이 느려진다.

즉 “지연은 어느 정도 감수하더라도 데이터 유실은 최소화하고 싶다”는 경우에 쓰는 절충안이다. 완전 비동기(빠르지만 유실 위험) ↔ 완전 동기(안전하지만 매우 느림) 그 사이의 중간 지점이라고 보면 된다.

정리

  • Master에는 쓰고, 하나 이상의 Slave(Read Replica)로 binlog를 통해 변경 내역이 복제된다.
  • 쓰기는 Master로, 읽기는 Slave로 분산시켜서 DB 부하를 나누는 게 기본 전략이다.
  • 복제는 실시간이 아니라 약간의 지연이 있을 수 있다(Replication Lag) — 방금 쓴 데이터를 바로 읽어야 하는 요청은 Slave가 아니라 Master에서 읽어야 한다.
  • 지연에 민감한 서비스라면 semi-sync replication이나 지연 모니터링(Seconds_Behind_Master)을 함께 고려한다.
