EXPLAIN 결과 읽는 법 - type 컬럼과 옵티마이저

EXPLAIN의 type 컬럼(const/ref/range/index/ALL) 읽는 법과 옵티마이저의 역할, range와 index의 차이를 정리한다.

게시 2026/08/31
By Sooyoung Choi
읽는 시간 10분

슬로우 쿼리 로그 글에서 EXPLAIN을 “느린 쿼리를 분석하는 도구”라고 소개했는데, 이번엔 EXPLAIN 결과에서 가장 중요한 type 컬럼을 제대로 읽는 법을 정리한다.

옵티마이저(Query Optimizer)란

type을 보기 전에, 애초에 이 값을 누가 정하는지부터 짚고 가야 한다. 옵티마이저는 “이 쿼리를 어떤 방식으로 실행하는 게 제일 빠른지 미리 계산해서 결정해주는 MySQL 내부 컴포넌트”다.

1

SELECT * FROM orders WHERE user_id = 5 AND status = 'done';

이 쿼리 하나를 실행하는 데도 방법은 여러 가지다.

  • user_id 인덱스로 먼저 찾고 status는 걸러낼까?
  • status 인덱스로 먼저 찾고 user_id를 걸러낼까?
  • 복합 인덱스 (user_id, status)가 있으면 그걸 통째로 쓸까?
  • 그냥 인덱스 없이 전체를 훑을까?

개발자는 SQL로 “무엇을” 가져올지만 정하고, “어떻게” 가져올지는 정하지 않는다. 그 “어떻게”를 결정하는 게 옵티마이저의 역할이다.

옵티마이저는 테이블/인덱스의 통계 정보(전체 행 수, 각 값이 얼마나 다양한지 = 카디널리티 등)를 바탕으로, 여러 실행 계획의 비용(cost)을 계산해서 가장 낮은 것을 선택한다. EXPLAIN으로 보는 결과는 “옵티마이저가 최종적으로 고른 실행 계획”을 보여주는 것이다.

통계 정보가 오래돼서 실제 데이터 분포와 다르면, 옵티마이저가 더 나쁜 선택을 할 때도 있다 (이 경우 ANALYZE TABLE로 통계를 갱신한다). 그래서 “인덱스를 만들어놨으니 당연히 잘 쓰겠지”가 아니라, EXPLAIN으로 실제로 그 인덱스가 쓰였는지 직접 확인하는 습관이 중요하다.

type 컬럼 — 어떻게 데이터를 찾았는지

좋은 것부터 나쁜 것 순서로 정리하면 다음과 같다.

type 의미 속도
const PK/UNIQUE로 딱 1건 조회. 값이 이미 상수처럼 확정됨 최고
eq_ref JOIN에서 상대 테이블의 PK/UNIQUE로 딱 1건씩 매칭 매우 좋음
ref 인덱스로 여러 건 조회 (동등 비교, =) 좋음
range 인덱스로 범위 조회 (BETWEEN, >, <, IN) 보통
index 인덱스 전체를 처음부터 끝까지 스캔 안 좋음
ALL 전체 테이블 스캔. 인덱스를 아예 못 씀 최악

실무에서 제일 중요한 건 type이 ALL로 나오면 안 된다는 것이다. ALL은 B+Tree 글에서 다룬 “인덱스 없이 전체 스캔”하는 상황 그대로다.

-- users(id PK, email UNIQUE, name)

EXPLAIN SELECT * FROM users WHERE id = 5;
-- type: const (PK로 딱 1건)

EXPLAIN SELECT * FROM users WHERE email = 'a@test.com';
-- type: const 또는 ref (UNIQUE 인덱스가 있으면)

EXPLAIN SELECT * FROM users WHERE name = '철수';
-- type: ALL (name에 인덱스가 없으면 전체 스캔!)

EXPLAIN SELECT * FROM users WHERE id BETWEEN 1 AND 100;
-- type: range (PK로 범위 조회)

range vs index — 왜 range가 더 좋은가

둘 다 인덱스를 쓰긴 하지만, “인덱스의 얼마만큼을 읽느냐”가 다르다.

range — 인덱스의 일부분만 읽음

1
2

EXPLAIN SELECT * FROM orders WHERE id BETWEEN 100 AND 200;
-- type: range

인덱스는 정렬된 트리 구조(B+Tree)다. id BETWEEN 100 AND 200이면, MySQL은 트리를 타고 내려가서 id = 100이 있는 리프 노드를 바로 찾아낸 다음, 그 지점부터 리프 노드끼리 연결된 걸 따라 id = 200이 나올 때까지만 쭉 읽는다. 딱 필요한 구간만 읽는다.

index — 인덱스 전체를 처음부터 끝까지 다 읽음

1
2
3

EXPLAIN SELECT id FROM orders ORDER BY id;
-- 조건(WHERE)이 없어서 어디서부터 어디까지 읽어야 할지 좁힐 수가 없음
-- type: index (인덱스를 처음부터 끝까지 전부 훑음)

WHERE 조건이 없거나, 있어도 그 인덱스로 범위를 좁힐 수 없다면 “조건에 안 맞는 부분은 건너뛴다”는 게 애초에 불가능하다. 그래서 인덱스의 처음 리프 노드부터 마지막 리프 노드까지 전부 훑어야 한다.

index는 왜 ALL보다는 나은가

둘 다 “전체를 다 읽는다”는 점은 같아 보이지만, index가 ALL보다 나은 이유가 있다.

  • ALL: 테이블 원본 데이터를 통째로 읽는다 (모든 컬럼, 큰 용량).
  • index: 인덱스만 읽는다. 인덱스는 보통 원본 테이블보다 훨씬 작고(필요한 컬럼만 담고 있음), 이미 정렬돼 있어서 ORDER BY가 있어도 별도 정렬(filesort) 없이 순서대로 읽기만 하면 된다.

즉 range가 제일 좋은 이유는 “필요한 구간만 읽어서”, index가 ALL보다 나은 이유는 “똑같이 전체를 읽어도 더 작고 이미 정렬된 것을 읽어서”다.

1
2

const/eq_ref  →  ref  →  range  →  index  →  ALL
"딱 1건"        "여러 건"  "구간만"   "전체(인덱스)"  "전체(테이블)"

오른쪽으로 갈수록 “얼마나 많이, 얼마나 무거운 걸 읽어야 하는지”가 늘어나는 순서다.

같이 보면 좋은 컬럼들

  • key: 실제로 어떤 인덱스를 썼는지. possible_keys(쓸 수 있었던 후보)엔 있는데 key가 NULL이면, 옵티마이저가 그 인덱스를 안 쓰기로 판단한 것이다 (데이터가 적어서 전체 스캔이 더 낫다고 판단했을 수도 있음).
  • rows: 이 단계에서 몇 건을 훑을 것으로 예상하는지. 실제 결과 건수가 아니라 추정치라는 게 포인트다 — 이 값이 실제 필요한 결과 수보다 훨씬 크면 비효율적인 신호다.
  • key_len: 실제로 사용한 인덱스의 바이트 길이. 복합 인덱스 중 일부 컬럼만 쓰였는지 확인할 때 유용하다 (전체 컬럼을 다 쓰면 key_len이 크고, 앞쪽 일부만 쓰이면 작다).

정리

  • EXPLAIN은 옵티마이저가 통계를 바탕으로 계산해서 최종적으로 고른 실행 계획을 보여준다.
  • type은 const/eq_ref(최고) → ref → range → index → ALL(최악) 순으로 읽는다. ALL은 항상 의심해야 한다.
  • range는 필요한 구간만 읽어서 빠르고, index는 전체를 읽긴 해도 ALL보다 작고 정렬된 데이터를 읽어서 그나마 낫다.
  • key(실제 쓰인 인덱스), rows(예상 스캔 건수), key_len(인덱스 활용 범위)도 같이 보면 어디가 병목인지 더 정확히 짚어낼 수 있다.
