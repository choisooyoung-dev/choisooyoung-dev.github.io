N+1 문제

ORM에서 흔히 발생하는 N+1 문제의 원인과, TypeORM으로 해결하는 방법(relations, QueryBuilder, IN절 배치 조회)을 정리한다.

게시 2026/08/31
By Sooyoung Choi
읽는 시간 8분

N+1 문제란?

리스트 1개를 조회했는데, 그 리스트의 각 항목마다 관련 데이터를 추가로 조회하는 쿼리가 N번 더 나가는 문제. 총 쿼리 수가 “1(리스트 조회) + N(항목 개수만큼 추가 조회)” 형태가 돼서 N+1이라고 부른다.

예시로 보면 바로 이해된다

주문(orders) 목록을 가져오면서, 각 주문의 유저(user) 정보도 같이 보여줘야 하는 상황.

1
2
3
4

const orders = await orderRepository.find(); // 쿼리 1번: 주문 10개 조회

for (const order of orders) {
  const user = await userRepository.findOne({ where: { id: order.userId } });
  // 이 줄이 orders.length(=10)번 실행됨!
  console.log(user.name);
}

실제 나가는 쿼리:

1
2
3
4
5
6

SELECT * FROM orders;
-- 아래가 orders 개수만큼 반복
SELECT * FROM users WHERE id = 1;
SELECT * FROM users WHERE id = 2;
SELECT * FROM users WHERE id = 3;
-- ...

주문이 10개면 11번의 쿼리, 주문이 10,000개면 10,001번의 쿼리가 나간다.

왜 문제인가

쿼리 하나하나가 아무리 빨라도(예: 1ms), DB 왕복 자체에 드는 네트워크 latency가 매번 붙는다. 쿼리 1번 실행에 1ms만 걸려도 네트워크 왕복이 5ms라면, 10,000번 반복 시 5만ms(50초)가 순수하게 왕복 시간으로 날아간다. 실제 DB 처리 시간보다 “쿼리를 왕복하는 횟수” 자체가 병목이 되는 것이다.

왜 이런 코드를 짜게 되는가

보통 의도치 않게 발생한다. 특히 리스트를 조회한 다음 각 항목의 연관 관계(relation)를 하나씩 접근할 때(order.user.name처럼), 또는 ORM의 lazy loading(필요할 때 그때그때 조회)이 관계 접근 시점마다 쿼리를 새로 날린다는 걸 모르고 쓸 때 생긴다.

Eager Loading vs Lazy Loading

  • Lazy Loading (지연 로딩): 연관 데이터를 필요한 시점에 그때그때 따로 가져오는 방식. 리스트를 순회하며 각 항목의 관계에 접근할 때마다 쿼리가 새로 나가서, 반복문 안에서 쓰면 N+1 문제로 이어진다.
  • Eager Loading (즉시 로딩): 연관 데이터를 처음 조회할 때 미리 같이(JOIN으로) 가져오는 방식. 쿼리 1번으로 끝난다.
1

4

// Lazy — 나중에 order.user 접근할 때마다 추가 쿼리 발생
const orders = await orderRepository.find();
orders[0].user.name; // 이 시점에 추가 쿼리!

// Eager — 처음 조회할 때 미리 JOIN해서 다 가져옴
const orders = await orderRepository.find({
  relations: { user: true },
});
orders[0].user.name; // 이미 다 채워져 있음, 추가 쿼리 없음

“언제 데이터를 가져오느냐”의 차이다. N+1 문제는 Lazy 방식이 리스트 안에서 반복적으로 발생할 때 터지고, 그걸 막는 게 Eager Loading이다.

해결 방법 (TypeORM 예시)

핵심은 “N번 나눠서 하지 말고, 한 번에(또는 훨씬 적은 횟수로) 가져오자”다.

1. Repository API + relations (Eager Loading)

1
2
3

const orders = await orderRepository.find({
  relations: { user: true },
});

실제 나가는 쿼리 (JOIN 1번):

1
2
3
4
5

SELECT
  order.id, order.userId, order.amount,
  user.id, user.name, user.email
FROM orders order
LEFT JOIN users user ON user.id = order.userId;

2. QueryBuilder로 직접 JOIN

관계 설정이 복잡하거나 조인 조건을 더 세밀하게 다루고 싶을 때는 QueryBuilder를 직접 쓴다.

1
2
3
4
5

const orders = await orderRepository
  .createQueryBuilder('order')
  .leftJoinAndSelect('order.user', 'user') // "user" 관계를 JOIN해서 같이 SELECT
  .where('order.createdAt >= :from', { from: '2026-01-01' })
  .getMany();

실제 나가는 쿼리:

1
2
3
4
5
6

SELECT
  order.id AS order_id, order.userId AS order_userId,
  user.id AS user_id, user.name AS user_name
FROM orders order
LEFT JOIN users user ON user.id = order.userId
WHERE order.createdAt >= '2026-01-01';

leftJoinAndSelect가 핵심이다. leftJoin만 쓰면 조인은 하되 그 결과를 엔티티에 채워주지 않아서(SELECT 절에 넣어주지 않아서), 여전히 order.user에 접근할 때 추가 쿼리가 나갈 수 있다. leftJoinAndSelect를 써야 JOIN한 데이터까지 같이 담아준다.

3. IN절 배치 조회 (JOIN이 힘든 경우)

서로 다른 DB(샤딩 환경 등)에 있거나, 관계가 복잡해서 바로 JOIN하기 어려운 경우엔 이 방식을 쓴다.

const orders = await orderRepository.find(); // 쿼리 1번
const userIds = [...new Set(orders.map((o) => o.userId))]; // 중복 제거

const users = await userRepository.find({
  where: { id: In(userIds) }, // 쿼리 1번 (WHERE id IN (...))
});

const userMap = new Map(users.map((u) => [u.id, u]));
const result = orders.map((o) => ({
  ...o,
  user: userMap.get(o.userId),
}));

실제 나가는 쿼리 (딱 2번):

1
2

SELECT * FROM orders;
SELECT * FROM users WHERE id IN (1, 2, 3, 4, 5);

쿼리는 1번에서 2번으로 늘었지만, 데이터를 가져온 뒤 메모리에서 매칭하는 방식이라 데이터 양과 상관없이 항상 쿼리 2번으로 끝난다.

주의: Eager Loading을 항상 쓰면 되는 건 아니다

관계 데이터가 실제로 안 쓰이는 상황에서도 매번 JOIN해버리면, 필요 없는 데이터까지 계속 가져오게 되어 오히려 손해다. N+1을 막으려고 무조건 JOIN을 다 걸어두는 것도 정답은 아니고, “이 화면/API에서 진짜로 필요한 관계가 뭔지”를 보고 그때그때 필요한 relation만 로딩하는 게 맞다.

정리

  • N+1 문제는 리스트 조회(1번) + 각 항목마다 연관 데이터 추가 조회(N번)로 쿼리가 폭증하는 문제다.
  • 원인은 대부분 ORM의 lazy loading을 의식하지 못하고 관계에 접근할 때 생긴다.
  • 해결법은 크게 두 가지: JOIN으로 한 번에(relations, leftJoinAndSelect) 또는 IN절로 배치 조회 후 메모리에서 매칭.
  • 관계 데이터가 안 쓰이는 곳까지 무조건 JOIN하는 것도 낭비이므로, 실제 필요한 곳에만 선택적으로 적용한다.
