MySQL 스토리지 엔진 (InnoDB vs MyISAM)

InnoDB와 MyISAM 스토리지 엔진의 차이를 트랜잭션 지원, 락 단위, FK 제약조건 중심으로 비교 정리한다.

게시 2026/08/25
By Sooyoung Choi
읽는 시간 4분

MySQL의 대표적인 스토리지 엔진 두 가지, InnoDB와 MyISAM을 비교해본다.

InnoDB

  • 트랜잭션 지원 (커밋/롤백 가능)
  • Row(행) 단위 락 — 필요한 행만 잠그기 때문에 동시성이 좋다
  • FK(외래키) 제약조건 지원
  • 장애 시 복구 기능 제공 (redo log 기반)
  • MySQL / MariaDB 기본 엔진, 사실상 표준

MyISAM

  • 트랜잭션 지원 X (커밋/롤백 개념 자체가 없음)
  • 테이블 전체 단위로 락 — 한 행만 수정해도 테이블 전체가 잠겨서 동시에 여럿이 못 씀
  • FK 없음

만약 “재고 차감 + 로그 생성” 로직을 MyISAM으로 만든다면?

EX) 재고를 차감하고, 그 내역을 로그 테이블에 남기는 두 단계 작업을 MyISAM 테이블로 처리한다고 가정

  • 동시 접근 문제는 테이블 락으로 어떻게든 막을 수는 있다.
  • 하지만 트랜잭션이 없어서 롤백이 안 된다는 게 가장 큰 문제다.
    • 재고 차감은 성공했는데, 그 직후 로그 생성이 실패해도 되돌릴 방법이 없다.
    • → 재고는 줄었는데 로그는 안 남는 상황이 실제로 발생할 수 있다. (원자성 깨짐)
  • 테이블 전체 락이라, 서로 관련 없는 행(row)을 건드리는 요청까지도 전부 테이블 락에 걸려서 기다려야 한다.
    • 다들 순서대로 기다려야 하니 병목현상이 생긴다.

정리하면:

  • 동시성 문제 → 락으로 어떻게든 막을 수는 있다 (다만 테이블 락이라 성능은 크게 떨어진다)
  • 원자성 문제 → 트랜잭션이 없으면 애초에 해결이 불가능하다

즉 MyISAM은 락만으로 동시성은 흉내 낼 수 있어도, 트랜잭션이 없다는 근본적인 한계 때문에 원자성이 필요한 로직(재고 차감처럼 여러 단계가 하나로 묶여야 하는 작업)에는 적합하지 않다.

비교 정리

  InnoDB MyISAM
트랜잭션 O X
락 단위 Row(행) 단위 테이블 전체
FK 제약조건 O X
장애 복구 O (redo log) 약함
동시성 좋음 나쁨 (테이블 락)
적합한 경우 대부분의 일반적인 서비스 (읽기/쓰기 동시 발생) 읽기 위주, 쓰기가 거의 없는 특수한 경우

결론

지금은 특별한 이유가 없다면 InnoDB를 기본으로 쓰는 게 맞다. MyISAM은 트랜잭션과 FK가 필요 없고, 쓰기가 거의 없는 극히 제한적인 경우(예: 아카이브성 읽기 전용 테이블)가 아니라면 실무에서 선택할 이유가 거의 없다. 실제로 MySQL 5.5부터 기본 엔진 자체가 MyISAM에서 InnoDB로 바뀌었다.
