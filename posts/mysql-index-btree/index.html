MySQL 인덱스 자료구조 - B+Tree

MySQL 인덱스의 실체인 B+Tree 자료구조를 B-Tree와 비교하고, WHERE/ORDER BY와의 관계를 정리한다.

게시 2026/08/25
By Sooyoung Choi
읽는 시간 5분

MySQL(InnoDB)의 인덱스는 내부적으로 B+Tree라는 정렬된 트리 구조로 저장된다.

트리(Tree)란?

찾고 싶은 값이 있을 때, 맨 위(루트)부터 값을 비교하면서 내려가며 관련된 가지만 타고 내려간다. 전체를 다 뒤지지 않고 필요한 경로만 따라가기 때문에 속도가 빨라진다.

              [ 루트, Root ]           ← 맨 위 시작점
              /            \
          [ A ]            [ B ]      ← 노드(Node): 트리를 이루는 한 칸
         /     \                \
      [ C ]   [ D ]             [ E ]  ← 자식(Child): 한 노드 아래로 연결된 노드
      -----------------------------
      C, D, E                        ← 리프(Leaf): 더 이상 자식이 없는 노드
  • 루트(Root): 트리의 맨 위, 탐색이 시작되는 지점
  • 노드(Node): 트리를 이루는 하나하나의 칸(값 + 다음 노드로의 연결)
  • 자식(Child): 한 노드 아래로 연결된 노드
  • 리프(Leaf): 더 이상 자식이 없는 가장 아래 노드 — 실제 값(또는 데이터 위치)이 저장되는 곳

B-Tree와 B+Tree의 차이

이름이 비슷해서 헷갈리기 쉬운데, MySQL(InnoDB)이 실제로 쓰는 건 B-Tree가 아니라 B+Tree다.

  B-Tree B+Tree
데이터 저장 위치 루트/중간 노드에도 데이터 저장 리프 노드에만 데이터 저장
중간 노드의 역할 데이터 + 길찾기 둘 다 길찾기(인덱스) 전용
리프 노드끼리 연결 X O (연결 리스트로 서로 이어짐)
범위 검색(BETWEEN, >, ORDER BY) 상대적으로 느림 리프만 순서대로 훑으면 되므로 빠름

B+Tree는 중간 노드에는 실제 데이터 없이 “다음 어디로 가야 하는지”만 담고, 진짜 데이터는 전부 리프 노드에만 있다. 그리고 그 리프 노드들이 서로 옆으로 연결되어 있어서, 범위 검색을 할 때 중간 노드를 오가지 않고 리프만 쭉 따라가면 된다. 그래서 정렬/범위 조회가 많은 DB 인덱스에 B+Tree가 훨씬 유리하다.

인덱스 = B+Tree 그 자체

  • 컬럼에 인덱스를 만드는 순간, 그 인덱스는 B+Tree 구조로 정렬되어 저장된다.
  • 즉 B+Tree는 “인덱스를 빠르게 만들어주는 부가 기능”이 아니라, 인덱스가 저장되는 자료구조 그 자체다.

WHERE, ORDER BY와의 관계

  • WHERE로 조건 검색할 때 → 루트에서부터 비교하며 내려가서 조건에 맞는 리프만 빠르게 찾는다.
  • ORDER BY로 정렬할 때 → 리프 노드가 이미 정렬된 상태로 연결되어 있으므로, 다시 정렬할 필요 없이 리프를 순서대로 읽기만 하면 된다.

인덱스가 없으면?

상황 인덱스 없을 때 동작
WHERE로 조건 검색 전체 스캔(Full Table Scan) — 테이블의 모든 행을 처음부터 끝까지 다 확인
ORDER BY로 정렬 직접 정렬(Using filesort) — 조회된 결과를 그 자리에서 다시 정렬

둘 다 데이터가 많아질수록 성능이 크게 떨어지는 원인이 된다. EXPLAIN으로 쿼리를 확인했을 때 type: ALL(전체 스캔)이나 Extra: Using filesort가 보이면, 해당 컬럼에 인덱스를 거는 걸 고려해봐야 한다.

정리

  • MySQL 인덱스의 실체는 B+Tree다.
  • 중간 노드는 길찾기용, 실제 데이터는 리프에만 있고 리프끼리 연결되어 있어서 범위 검색/정렬에 특히 강하다.
  • 인덱스가 없으면 WHERE는 전체 스캔, ORDER BY는 직접 정렬(filesort)로 처리되어 느려진다.
